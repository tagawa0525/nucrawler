# LLM の呼び出しを並行にする（ロックの戦略の見直し）

## 背景

2026-09-29 時点では、LLM を呼ぶ処理（crawl の要約・採点・和訳・見出しの和訳・語彙の整理、redo、
profile suggest、eval --profile）は、すべて 1 つのロック `llm.lock` を取り、プロセスごと 1 本ずつ動く。
各ステージの中でも `claude -p` を 1 回ずつ順に呼ぶ。

- 呼び出しの大半は応答待ち（和訳で 1 件 20〜30 秒）なので、過去分をまとめて処理しても 5 時間枠を使い切れない
  （2026-09-29 の深夜は 55% までしか使えなかった）
- 長い redo の間は、和訳の依頼（15 分ごとの timer）や定時の crawl が待たされる（1 時間以上待った例がある）

`llm.lock` が実際に守っているのは次の 3 つで、プロセスを 1 本に絞ることでまとめて満たしている。

1. 同じ記事・同じステージ・同じモデルを 2 か所で同時に処理しない（二重処理）
2. クォータの判定に、ほかの実行の呼び出しを入れる（起動時に DB の最新の使用率を読むだけなので、
   並行するとほかの実行の呼び出しが見えない）
3. 同時に呼び出す数（暗黙に 1）

## 方針

3 つをそれぞれの仕組みで守り、`llm.lock` をやめる。

| 守るもの         | 見直し後                                                                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 二重処理         | DB 上の作業の予約（`work_claims`）。キーは `stage_errors` と同じ（記事・ステージ・backend・model）。対象を選ぶときに予約中の記事を除き、選んだ記事を予約してから処理し、終われば外す。期限付きなので、プロセスが落ちても期限で外れる |
| クォータ         | 呼び出しの直前に毎回、DB の最新の使用率（`llm_calls` の最新の rate_limit）を読む                                                                                                                                                     |
| 同時に呼び出す数 | `llm.concurrency` 個のロックファイル（`llm-slot-N.lock`）を、呼び出しの間だけ 1 つ取る。プロセスをまたいだ上限になり、落ちても OS が解放する                                                                                         |

- `fetch.lock` は残す（取得は同じホストへの間隔を守るため、並行させない）
- 更新前の版と重ならないための `crawl.lock` の共有ロックも残す
- 語彙の整理（tidy）は、要約と同時に動いても DB のトランザクションで整合が保たれる（統合済みの語は統合先に付く）が、
  整理どうしは重ならないよう、記事によらない予約（1 つだけ）を取る
- 呼び出しの前の判定は、実行中の呼び出しの分だけ古い使用率を見るので、上限を最大 `llm.concurrency` 回分超え得る。
  既定の `llm.concurrency` は小さく（2）する

## PR の分け方（どこで止めても壊れない順）

1. 作業の予約：`work_claims` のマイグレーション、`Db::claim`（取れた分だけ返す）と解放（drop で外すガード）、
   対象を選ぶ 6 つのクエリ（`pending_digest`・`redo_digest`・`pending_translate`・`redo_translate`・
   `pending_score`・`pending_titles`）で予約中の記事を除く。訳語集の変更による作り直しは、先に決めた対象を
   予約してから処理する。各ステージが予約してから呼び、終われば外す。`llm.lock` は残すので振る舞いは変わらない
2. ロックの置き換え：クォータの判定で毎回 DB の使用率を読む、呼び出しの数の上限をロックファイルで設ける、
   `llm.lock` をやめる（tidy は記事によらない予約）。ここでプロセスどうしが並行する
3. プロセス内の並行化：各ステージで `llm.concurrency` 本の処理を同時に回す（予約があるので同じ記事は取らない）

## 予約の詳細（PR 1）

- テーブル `work_claims (article_id, stage, backend, model, expires_at)`、主キーは記事・ステージ・backend・model
- 期限は `llm.timeout_secs` の 2 倍（呼び出しはタイムアウトより長く続かないので、それを過ぎた予約は放置されたもの）
- 予約は `INSERT … ON CONFLICT DO UPDATE … WHERE work_claims.expires_at <= now` で取り、変わった行だけを
  取れたものとする（トランザクションを張らなくても、2 つのプロセスが同じ記事を取ることはない）
- 外すのはガードの drop（成功・失敗・中断・停止のどれでも外れる）。外せなかったときは警告だけ出す（期限で外れる）
