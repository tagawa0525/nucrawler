# 利用者の評価から、推薦の点数を補正する

## 背景

2026-09-29 時点で、一覧の並び順と表示の閾値は LLM の点数（`scores.score`、0〜100）だけで決まる。
LLM は関心プロファイル（分野と重み）と記事から採点し、利用者の反応は点数に効かない。
反応が推薦に効く経路は `profile suggest`（LLM が案を作り、人が取り込む）だけで、外部のレビュー（ChatGPT）から
「LLM 頼みに過ぎる」と指摘された。

計画 003（PR #106〜#110）で、反応の記録を整理した。

- 評価：`ratings(user_id, article_id, value 1..5, rated_at)`。「この記事を自分に推薦すべきだったか」を
  5 必読、4 読んでよかった、3 どちらでもない、2 不要、1 二度と出さないでほしい、で付ける。評価なしは行が無いこと。
  **正解のラベルはこれだけ**
- 既読（`reads`）とブックマーク（`bookmarks`）は印で、ラベルにしない。開いた記録（`events`）は行動の記録
- `eval` は、評価の違う記事の組の順位の当たり具合（一致率。2 値なら AUC と同じ）を採点のキーごとに出す

LLM の点数が関心を分けきれていないことは、実データでも見えている。2026-09-29 の本番では、
👎（今の評価 2）が 82〜88 点に、👍（今の評価 4）が 25〜45 点に付いていた。

## 方針

LLM の点数はそのまま残し、**評価から学んだ補正を足した点数（以下「推薦点」）**で並べ、閾値を判定する。
補正は Rust の中で計算し、LLM を呼ばない。評価を付けた直後の一覧から効く。

### モデル

記事 i の推薦点を、確率 p_i を 100 倍したものとする。

```text
z_i = a · x_i + b + Σ_f w_f · φ_if
p_i = σ(z_i)            （σ はロジスティック関数）
推薦点 = round(100 · p_i)
x_i = logit(clamp(LLM 点 / 100, 0.005, 0.995))
```

- 特徴 φ_if は 0/1 で、次の 4 種類。
  - `topic`：記事の要約（利用者が閲覧できる最新の digest）に付いたトピック。統合を反映した語（`artifact_topics` → `topics`）
  - `source`：記事のソース（`articles.source_id`）
  - `interest`：その点数が当たった関心分野（`score_matches` の kind `interest`）
  - `exclude`：その点数が当たった推薦しない話題（`score_matches` の kind `exclude`）
- 目的変数は、評価を 0〜1 に写した `y_i = (評価 − 1) / 4`（1→0、3→0.5、5→1）。交差エントロピーは 0〜1 の目的変数を
  そのまま扱えるので、評価 3 も「中間」として学習に使える。
- 事前分布（L2 の正則化）は **今の振る舞いを中心に置く**：a は 1、b と w_f は 0 に向けて縮める。
  - 評価が 0 件なら a = 1・b = 0・w = 0 で、推薦点は LLM 点と同じになる（0 と 100 だけは 1 と 100 になる）。
    評価が少ないうちは補正が小さく、評価が増えるほど効く。
  - 強さは設定 `[recommend] prior_strength`（既定 20。下の「実装で変えたこと」）。
- 損失：`Σ_i CE(y_i, p_i) + (λ/2)((a−1)² + b² + Σ_f w_f²)` を Newton 法で最小化する。未知数は 2 + 評価した記事に
  現れた特徴の数（本番ではトピック 72・ソース 21・関心分野 8 の一部で、100 程度まで）。ヘッセ行列は正定値なので、
  コレスキー分解で解く。標準ライブラリだけで書く（依存を足さない）。
- 学習に使う記事は、評価があり、今のプロファイルと採点のプロンプトの版で採点されているもの（一覧と同じく
  最新の digest の点数）。未採点の記事は推薦点を持たない（今と同じく未採点として扱う）。

### なぜこの形か

- LLM の点数を捨てずに入力の 1 つとして使い、「LLM がどの分野・ソースを過大・過小評価しているか」だけを学ぶ。
  評価が少ないうちに LLM の判断を上書きしない。
- 特徴は、既に DB にあり人が読める単位（トピック・ソース・関心分野）に限る。補正の理由をそのまま画面に出せる
  （例：「LLM 72 → 81：トピック 燃料 +6、ソース NRC +3」）。
- 埋め込み（文の類似度）は、モデルの実行という依存が増えるので使わない。トピックの語彙（72 語）で当面足りる。
- 暗黙の反応（開いた・ブックマーク・和訳の依頼）は、点数が高い記事ほど起きやすく、点数の結果であって正解ではない。
  ラベルにしない（効くと確かめられたら、別の計画で弱いラベルとして足す）。

### 評価（`eval`）

同じ評価で学習と評価をすると当たり具合が良く出すぎるので、**1 件ずつ外して学習し、外した 1 件を予測する**
（leave-one-out）。評価が 100 件でも、学習は 100 回で済む。

- 今のキーの行に、LLM 点の一致率と並べて、推薦点（leave-one-out）の一致率を出す。
- 推薦点で一覧・閾値を切り替えた後も、この比較で効いているかを確かめられる。

### 一覧への適用

- 並び順・閾値（`?min=N`、`web.min_score`）・確認枠の候補の判定は、推薦点で行う。
  - 確認枠は「推薦点が設定の閾値未満」の記事から無作為に選ぶ（見逃し率は推薦点に対して測る）。
- 推薦点は SQL の中で計算する（並び・絞り込み・件数の上限を SQL のまま保つため）。
  - 同梱の SQLite には `exp`・`ln` が無いので、rusqlite の `functions` 機能（既存の依存の機能）で
    `recommend_score(llm_score, a, b, weight_sum)` を接続ごとに登録する。
  - `weight_sum` は、記事の特徴に当たる重みの和を、重みの表（下記）との相関副問い合わせで求める。
- 補正のモデルは DB に置く。
  - `recommend_models(user_id PK, profile_hash, prompt_version, labels_count, labels_until, a, b, fitted_at)`
  - `recommend_weights(user_id, kind, key, weight, PRIMARY KEY (user_id, kind, key))`
  - 学習し直すのは、評価の件数・最後の評価の時刻・プロファイル・採点のプロンプトの版のどれかが、保存したモデルと
    違うとき。一覧・詳細・検索・JSON・MCP の読み出しの前に確かめ、違えばその場で学習し直す（1 秒かからない）。
    crawl は推薦点を使わないので学習しない。
- 画面
  - カードの点数は推薦点にする。LLM 点と違えば、点数の title に「LLM 72・補正 +9」を出す。
  - 詳細に、補正の内訳（効いた特徴と、その点数への寄与）を並べる。
- JSON・MCP：`score` は推薦点にし、`llm_score` を足す。

## 実装で変えたこと（PR 3 で分かったこと）

- **全体の係数（a・b）は学ばない。** 推薦点は `σ(x + Σ w_f)` で、特徴ごとの重みだけを学ぶ。LLM 点の傾き a と
  全体のずれ b を学ぶと、評価 1 件で全記事の点数が動き、評価した記事と特徴を共有しない記事まで補正された
  （既存のテストで、LLM 95 点に評価 2 を付けた 1 件だけで、ほかの記事が一覧から消えた）。
- **既定の強さは 20。** 補正が半分の強さに達するのは、その特徴の評価がおよそ「強さ ÷ p(1−p)」件
  （50 点付近で強さの 4 倍）そろったとき。1 件の評価は記事の特徴（4 つ前後）すべてに効くので、5 では評価 1 件で
  特徴を共有する記事が最大 8 点ほど動き、本番の評価 9 件で一覧の 64 記事中 61 記事が最大 20 点動いた。
  20 では最大 6 点、多くは ±3 点に収まる。
- **モデルは DB に保存しない。** 学習は数十ミリ秒で済むので、読み出しのたびに学習の材料（評価した記事ごとの
  LLM 点・特徴・評価）を読み、前と違えば学習し直して `Db` の中に持つ（プロセスごと）。評価・採点の件数などの
  目印で判断すると、最新の要約が変わった・トピックを統合した、といった材料の変化を取りこぼすため。
  重みは JSON のまま SQL に渡し（`json_each`）、推薦点は登録した関数 `recommend_score(llm_score, weight_sum)` で求める。
  保存する表（`recommend_models`・`recommend_weights`）とマイグレーションは作らない。

## PR の分け方

各 PR は TDD（RED のテストのコミット → GREEN の実装のコミット）で進める。

### PR 1 `feat/recommend-model`：補正のモデル（純粋な計算）

- `src/recommend.rs`：特徴（`Feature { kind, key }`）、学習の行（LLM 点・特徴・評価）、`fit`（Newton 法と
  コレスキー分解）、`Model::score`（推薦点）、`Model::contributions`（特徴ごとの寄与）。I/O を持たない。
- テスト：評価 0 件で LLM 点と同じ、低く評価したトピックの重みが負になる、1 件だけでは補正が小さい（縮める）、
  評価 3 は中間として効く、同じ入力で同じ結果、特徴の無い記事は a・b だけで決まる。
- この計画を docs/plans に置く。

### PR 2 `feat/recommend-eval`：評価の比較

- `db`：評価した記事の学習の行（今のキーの LLM 点と特徴）を読む。
- `eval`：今のキーの行に、推薦点（leave-one-out）の一致率を並べる。設定 `[recommend] prior_strength` を足す。

### PR 3 `feat/recommend-list`：一覧を推薦点で並べる

- マイグレーション：`recommend_models`・`recommend_weights`。
- 学習し直しの判定と保存、`recommend_score` の登録、一覧・検索・確認枠・JSON・MCP を推薦点に切り替える。
- カードの点数の title と、詳細の補正の内訳。README。

## この後（別の計画にする）

- 暗黙の反応（和訳の依頼・コメント・開いた記録・ブックマーク）を、eval で効くと確かめてから弱いラベルとして足す。
