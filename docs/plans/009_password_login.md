# ログイン ID とパスワードでの認証

## Context

これまで nucrawler はオーナー 1 人で使っていて、Web UI に認証は無い。
Tailscale の tailnet のアドレスで待ち受けて、ネットワークに入れる人を利用者とみなしてきた（README の「認証は無いので、Tailscale など信頼できるネットワークのアドレスで待ち受ける」）。

これを社内 LAN 内の複数の人に使ってもらう。条件は次のとおり。

- 使うのは社内 LAN の中だけ。インターネットには出さない
- 社内には Entra ID があるが、nucrawler の開発・稼働環境（個人の環境）からは使えない
- リバースプロキシは置かない。nucrawler が直接待ち受ける
- **HTTP のまま**にする（社内 CA などで証明書を用意できないため）。パスワードとセッションの Cookie は LAN に平文で流れる。
  これを承知のうえで「社内 LAN 内だけ」を前提とする

### DB はもう利用者ごと、Web は所有者に固定

星（`ratings`）・既読（`reads`）・ブックマーク（`bookmarks`）・開いた記録（`events`）・プロファイル（`profiles`）・採点（`scores`）・コメント・指摘は、
どれもキーに `user_id` を持っていて、利用者ごとに記録できる。`users.login` には「Tailscale-User-Login」と注記があり、利用者を見分ける列として用意してある。

一方、Web のハンドラは、利用者をいつも所有者（`users.is_owner = 1` の 1 行）にしている。

```rust
/// 利用者（今は所有者だけ）と、現在のプロファイルのハッシュ。
fn viewer(db: &Db) -> Result<(i64, Option<String>), DbError> {
    let user = db.owner_id()?;
    let hash = db.profile_hash(user)?;
    Ok((user, hash))
}
```

`src/web/server` のハンドラは、この `viewer()` を通して利用者を決めている（約 20 か所）。
そのため、誰がアクセスしても、所有者の星・既読・ブックマークを読み書きしてしまう。

## 方針

- 認証の方式は **ログイン ID（メールアドレス）とパスワード**
  - Entra ID（OIDC）は使えず、リバースプロキシに認証を任せることもできないので、アプリで持つ
  - `users.login` をログイン ID にする。将来 Entra ID に移るときも、この列を利用者の一意な値として使い続ければ、
    星・既読などのデータはそのまま残せる。今は OIDC を見越した抽象化は作らない
- **アカウントは管理者が CLI で発行する**
  - 自分で登録する機能は作らない
  - メールでのパスワードのリセットも作らない（メールの送信の仕組みが要らなくなる）。忘れたら管理者が CLI でリセットする
  - 管理者は所有者（`is_owner = 1`）。CLI は稼働ホストに入れる人しか使えないので、CLI の操作自体が管理者の確認を兼ねる
- **パスワードは argon2id でハッシュにして保存する**（`argon2` crate を足す）
  - 標準ライブラリにはパスワードのハッシュ関数も安全な乱数も無く、自作は危ないので、依存を足す理由がある
  - セッションのトークンの乱数も、この crate が使う OS の乱数（`OsRng`）から作る
- **セッションは DB に持つ**
  - ログインしたら 256 bit の乱数のトークンを作り、Cookie に入れ、`sessions` に保存する
  - トークンは DB に平文で置く。ハッシュにするには別の依存（SHA-256 など）が要る一方、DB を読めるのは稼働ホストに入れる管理者だけで、
    DB を読めればトークンが無くても記事も印もすべて読めるため
  - 有効期限はログインから 30 日。ログアウトで行を消す
  - 期限切れの行は、ログインでセッションを作るときに、全員の分をまとめて消す。古いトークンが再び送られるのを待つだけでは、
    捨てられた Cookie の行がいつまでも残るため。ログインの頻度は低く、消す行も少ないので、ここで消しても重くならない
  - Cookie は `HttpOnly`・`SameSite=Lax`・`Path=/`。HTTP なので `Secure` は付けられない
  - Cookie にも DB と同じ期限（`Max-Age` 30 日）を付ける。付けないとブラウザを閉じた時点で消え、30 日のログインにならない。
    ログアウトでは、同じ `Path` で `Max-Age=0` の Cookie を返して消す
  - `SameSite=Strict` にしない理由：フィードリーダーやチャットのリンクから詳細を開くと、Strict では Cookie が送られず毎回ログイン画面になる。
    書き込み（POST）は、今もある Origin と Host の一致の確認（`AppError::CrossSite`）で他サイトからの送信を防いでいるので、Lax で足りる
  - Cookie の読み書きは `Cookie` / `Set-Cookie` ヘッダーを直接扱う（1 つの値を読むだけなので、`axum-extra` などは足さない）
- **パスワードの条件**
  - 本人が決めるパスワードは 12 文字以上、1024 バイト以下。満たさなければ 400 で、設定画面に理由を出す
  - 上限は、極端に長い入力でハッシュの計算を重くされないため。上限はパスワードを受け取るすべての入口（ログイン・パスワードの変更の今と新しいパスワード）で、
    計算の前に確かめる（下の「パスワードの計算は 1 つの部品を通す」）。文字の種類の条件（大文字・記号など）は付けない。
    長さのほうが強さに効き、種類の条件は覚えにくいパスワードを生むだけのため
  - CLI が作る初期パスワードは、紛らわしい文字（`0` `O` `1` `l` `I`）を除いた英数字 20 文字（約 110 bit）。条件と同じ上限・下限の中に収まる
  - ログイン ID も 254 バイト（メールアドレスの上限）以下に限る
- **総当たり対策**
  - ログイン ID ごとに、最後に成功してから続けて失敗した回数 n（`failed_logins`）と、次に試せる時刻（`locked_until`）を持つ
    - 失敗を数えたとき、n が 5 以下なら待たせない。6〜9 なら `locked_until` を「その失敗の時刻 + 2^(n−6) 分」、10 なら「+ 15 分」にする。
      つまり 6 回目の失敗で 1 分、7 回目で 2 分、8 回目で 4 分、9 回目で 8 分、10 回目以降は 15 分
    - n は 10 で止める（10 のときに失敗しても 10 のまま）。待ち時間は 10 回目で上限に達し、それより先を数えても使わない。
      止めないと、待ち時間が過ぎるたびに 1 回ずつ失敗させるだけで n が増え続け、指数の計算が整数の範囲を超える。指数は n が 6〜9 のときだけ計算する
    - 待ち時間中の試行は、照合はする（応答の時間を揃えるため。下の「ログインの手順」）が、結果によらず失敗とし、n にも `locked_until` にも数えない。
      数えて待ち時間を延ばすと、相手が送り続ける限り本人が永久にログインできなくなるため
    - 成功したら n を 0、`locked_until` を NULL に戻す。リセットと停止でも戻す（「資格の失効は 1 つの操作にまとめる」）
  - ID ごとの回数は `users` の行に持つので、存在しない ID には効かない。ID を変えながら試す相手には、送り元の IP ごとの制限で対処する。
    回数はメモリに持つ（再起動で消えてよい）
    - IP ごとには、失敗の回数 m と最後に数えた失敗の時刻を持つ。最後に数えた失敗から 15 分過ぎていれば、m を 0 から数え直す。
      m が 21 以上（20 回を超えた）なら、最後に数えた失敗から 15 分、その IP は待たせる（ID ごとより多いのは、1 台から複数の人が打ち間違えることもあるため）。
      m も 21 で止める
    - IP の待ち時間中の試行は照合せずに失敗を返し（下記）、m にも時刻にも数えない。ID ごとと同じく、送り続けても待ち時間は延びない
    - IP の回数は、ログインに成功しても消さない。消すと、自分のアカウントを持つ人が「ほかの ID で数回失敗しては自分の ID で成功する」を繰り返し、
      IP の制限を受けずにほかの ID を試し続けられる。IP の回数は、失敗が 15 分途切れたときにだけ消える
    - メモリの量に上限を置く。IP を変え続ける相手を想定しているので、消す条件が無いと、失敗のたびに項目が増え続ける
      - 項目は、最後の失敗から待ち時間の上限（15 分）が過ぎたら消す。新しい失敗を記録するときに、期限の過ぎた項目をまとめて消す
      - 項目の数の上限は 4096。期限切れを消しても上限に達しているときは、最後の失敗がいちばん古い項目を消す。
        消された IP は数え直しになるが、上限まで IP を用意できる相手でも、照合の同時実行数の上限（下記）で CPU は守られる
    - IP は TCP の接続元（ソケットの相手のアドレス）から取る。`X-Forwarded-For` などの転送ヘッダーは使わない。
      リバースプロキシが無いので、接続元がそのまま利用者の端末で、ヘッダーは送り手が自由に書けるため
    - 数えるキーは IP アドレス（`IpAddr`）だけにし、ポートは含めない。`ConnectInfo` の `SocketAddr` には接続元のポートも入っていて、
      接続ごとに変わる。`SocketAddr` のまま数えると、接続し直すたびに別の送り手になり、回数が溜まらない
    - 今のサーバーは `axum::serve(listener, router(state))` で、接続元のアドレスをハンドラに渡していない。
      `into_make_service_with_connect_info::<SocketAddr>()` で渡し、ハンドラは `ConnectInfo<SocketAddr>` で受け取る。テスト用のサーバーも同じにする
    - IP が待ち時間中なら、照合せずにすぐ失敗を返す。IP の待ち時間は送り手自身の失敗だけで決まり、どの ID を送ったかによらないので、
      応答が速くても ID の有無は分からない
- **パスワードの計算は 1 つの部品を通す**
  - argon2id の計算（照合とハッシュの作成）は 1 回が重い。Web でこれを行うのはログインの照合だけでなく、パスワードの変更（今のパスワードの照合と、
    新しいパスワードのハッシュの作成）もある。入口ごとに制限を書くと、どこかで抜ける
  - そこで、Web サーバーの argon2id の計算は、すべて 1 つの部品（例えば `PasswordHasher`。`AppState` に持つ）を通す。部品が次の 4 つをまとめて受け持つ
    - 長さの上限：1024 バイトを超える入力は、計算せずに断る。ログインでは失敗の共通の応答を返し、IP ごとの失敗に数える
      （長さは送り手が決めるもので ID の有無によらないので、計算しないで速く返しても ID の有無は漏れない）。パスワードの変更では 400
    - 同時に計算する数の上限：2 つ（セマフォ）。IP を変えられても、ログインしている利用者が変更の要求を並べて送っても、CPU を使い切られない
    - 待たせる数の上限：許可を待たず（`acquire().await` は待つ要求の数に上限が無い）、`try_acquire_owned` で取り、空きが無ければすぐに 503（「混み合っています」）を返す。
      503 は送った ID によらないので ID の有無は漏れず、IP ごとの失敗にも数えない（計算していないため）
    - 計算の場所：非同期のタスクの中ではなく `spawn_blocking` で行う（DB の処理と同じ）。非同期のまま計算すると tokio のワーカーが止まり、ほかの要求が遅れる。
      取った許可（`OwnedSemaphorePermit`）はクロージャに移し、計算が終わったときに返す。要求が途中で切られても `spawn_blocking` の計算は止まらないので、
      許可を非同期の側で持つと、切られた時点で許可が返り、上限を超えて計算が走る
  - 計算は DB のロックの外で行い、ほかの要求を待たせない
  - **照合から失敗の記録までを、1 つの `spawn_blocking` にまとめる**
    - 要求の処理（非同期のタスク）は、接続が切れると途中で捨てられる。照合の結果を待った後で失敗を記録する形だと、照合を始めた直後に接続を切れば、
      重い計算は最後まで走るのに、IP ごとにも ID ごとにも失敗が数えられない。これを繰り返せば、計算の枠 2 つを占め続けながら、制限を受けずに試せる
    - そこで、ログインの手順（下の 1.〜3.：読む・照合・判定して書く）と、IP ごとの失敗の記録を、許可と一緒に 1 つの `spawn_blocking` のクロージャに入れる。
      `spawn_blocking` のクロージャは、待っている要求が捨てられても最後まで走るので、照合したものは必ず記録される。
      クロージャの中では DB の `Mutex` を 1. と 3. のときだけ取り、照合の間は放す
    - パスワードの変更も同じく、今のパスワードの照合・ID ごとの失敗の記録・新しいパスワードの書き込みを 1 つのクロージャに入れる
  - CLI（`user add`・`reset-password`）のハッシュの作成は、稼働ホストの利用者が別のプロセスで行うので、この部品を通さない
- **ログインの手順**：DB を読む、ロックの外で照合する、DB に書く、の 3 段階に分かれる。段階の間に、ほかの要求（リセット・停止・ほかのログインの失敗）が
  状態を変えうる。そこで、分岐をすべて最後の書き込みのトランザクションに集める
  1. 読む：ログイン ID から、今のパスワードのハッシュを読む。ID が無い、またはパスワードが NULL なら、ダミーのハッシュを使う。
     ID ごとの待ち時間はここでは見ない
  2. 照合：どの場合でも、1. のハッシュに対して照合を 1 回行う（ダミーなら結果は必ず失敗）
  3. 書く：1 つのトランザクションで、利用者の行を読み直して判定する
     - 成功とするのは、照合が通り、パスワードのハッシュが 1. で読んだものと同じで、ID ごとの待ち時間中でないときだけ。このときセッションを作り、失敗の回数を 0 に戻す
     - ハッシュが変わっていれば（照合の間にリセット・停止・本人の変更があった）、古いパスワードでの照合なので失敗とする。
       ハッシュには毎回違うソルトが入るので、同じパスワードを設定し直しても一致しない
     - それ以外は失敗とし、ID があれば失敗の回数と待ち時間を更新する
  - ID ごとの待ち時間を 3. で判定するので、待ち時間中の ID でも、存在しない ID と同じく照合を行い、同じ時間がかかる。
    どの ID を知っていても、ロックさせてから応答の速さを比べる、といった方法では存在を確かめられない
  - 失敗の応答はすべて同じにする。ID が無い、パスワードが違う、待ち時間中（ID ごと・IP ごと）、パスワードが NULL、照合中に変わった、のどれでも、
    同じ文言（「ログイン ID かパスワードが違うか、失敗が続いたため今はログインできません」）と同じ状態コードを返す
- **ログインしていない要求**
  - 画面（GET）はログイン画面に回し、ログイン後に元の画面へ戻す。戻り先は `next` の値で受け取る
  - `next` は利用者が書き換えられるので、他サイトへ飛ばす（オープンリダイレクト）のに使われないようにする。
    文字列の形（`/` で始まる、`//` で始まらない）で判定すると、ブラウザの URL の解釈とずれる。
    例えば `/\evil.example` はブラウザでは `http://evil.example/` になり、フォームで `%5C` と送っても同じになる。
    そこで、ブラウザと同じ規則（WHATWG URL）で解釈する `url` crate（既存の依存）を使う
    - `http://{要求の Host}/` を基準に `next` を解釈し、結果のスキーム・ホスト・ポートが基準と同じときだけ使う。違えば `/` に戻す
    - リダイレクト先は、解釈した結果の絶対 URL にする。パスだけを返すと、解釈で `//evil.example` のようなパスになったときに、
      ブラウザがまた別のホストとして読んでしまうため。絶対 URL ならホストが決まっていて、読み違いが起きない
  - ログインとログアウトの POST にも、ほかの POST と同じ Origin と Host の一致の確認を掛ける（他サイトから別のアカウントでログインさせられるのを防ぐ）
  - JSON API（`/api/...`）と POST は 401 を返す。画面の JavaScript が使う `/api/marks` などはブラウザの Cookie で通る
- **フィード（`/feed.xml`）は利用者ごとのトークンで読む**
  - フィードリーダーはログインできないので、Cookie の代わりに URL のトークン（`/feed.xml?token=...`）で利用者を決める
  - トークンは `users.feed_token` に持ち、設定画面に購読用の URL を出す。作り直すと古い URL は使えなくなる
  - トークンはセッションと同じく、OS の乱数から作る 256 bit の値（URL にそのまま入る 16 進の文字列）。
    セッションと同じく、URL を知っていれば読めるので、推測できない長さにする
  - トークンの無いアクセスは 401
  - Atom の `rel="self"` のリンクは、今は `{base}/feed.xml` に固定している（`web::feed::atom`）。このままだとフィード自身が示す URL が 401 になり、
    それを使って購読し直すリーダーで読めなくなる。そこで `atom()` に、トークンを含めた購読用の URL を渡し、self のリンクにする
- **管理者だけができること**：訳語集の編集（`/glossary` への POST）と、指摘の受付箱（`/reports` の閲覧と、`/reports/{id}` での処理）
  - 訳語集は全員の和訳に効く共有のデータで、和訳は所有者の LLM の枠で作るため
  - 指摘は管理者に宛てたもので、自由記述の補足（`note`）と管理者の返事（`reply`）を含む。今の `Db::reports` は利用者で絞らず全件を返すので、
    受付箱をほかの利用者に見せると、ほかの人の指摘が読めてしまう
  - 指摘を出すこと・訳語集を見ることは全員ができる。一般の利用者が見られる指摘は、自分が出したものだけ（詳細の画面で、対応状況と返事を確かめるため）。
    `Db::reports` に出した人で絞る指定を足し、一般の利用者のときは自分の分に絞る。設定画面の受付中の件数（`report_counts`）も管理者にだけ出す
  - 管理者でなければ 403
  - 画面にも出し分ける。今の `glossary_page` と `reports_page` は、編集・削除・対応のフォームをいつも出している。
    ハンドラで 403 を返すだけだと、一般の利用者には押すと必ず失敗するフォームが並ぶ。描画に `is_admin` を渡し、管理者でなければ管理用のフォームを出さない
  - 運用の警告も管理者だけに出す。今はどの画面も `Db::warnings` を読み、ソースの取得や LLM の失敗を、生のエラー文（取得した URL を含む）のまま画面の上に出している。
    一般の利用者には、中の URL やバックエンドの診断を見せる理由が無く、見ても対処できない
    - 画面ごとに `warnings(db)` を呼ぶ今の形では、出し分けを画面ごとに書くことになり、どれかで漏れる。
      そこで、画面の共通の部分（`Page`）を利用者から作る関数を 1 つにし、その中で、管理者のときだけ警告を読む。どの画面もこの関数を通す
- **パスワードの変更**は、本人が設定画面から行う（今のパスワードと新しいパスワードを入れる）
  - 変えたら、今の要求のものも含めて、その人のセッションをすべて消し、フィードのトークンも消す。要求元には新しいセッションのトークンを発行して Cookie を差し替える（同じトランザクション）
    - 今のセッションを残すと、その Cookie を写し取っている相手も同じセッションなので、パスワードを変えても使い続けられる
    - フィードのトークンも同じ理由で消す。セッションを盗んだ相手は設定画面でフィードの URL を読めるので、残すとパスワードを変えた後もフィードで読み続けられる。
      本人は設定画面でフィードの URL を作り直し、購読し直す
  - 今のパスワードの照合も、ログインと同じく ID ごとの失敗の回数（`failed_logins`・`locked_until`）に数える。
    数えないと、盗んだセッションから今のパスワードを何度でも試せ、当てた後にパスワードを変えてアカウントを奪える
    - ID ごとの待ち時間中は、今のパスワードが正しくても変更を断る（ログインと同じ）
    - 失敗で待ち時間に入ったとき（n が 6 以上になったとき）は、その人のセッションをすべて消す。盗まれたセッションで試している相手を締め出すため。
      本人もログインし直しになるが、待ち時間が過ぎればログインできる
- **認証の状態を書き換える操作は、確認と書き込みを 1 つのトランザクションで行う**
  - 認証の状態（パスワード・セッション・フィードのトークン・失敗の記録）を書き換える操作は、ログイン・本人のパスワードの変更・フィードのトークンの作り直し・
    ログアウト・停止・リセットがある。どれも、要求を受けてから書き込むまでの間に、別の操作が状態を変えうる。
    例えば、パスワードの変更で今のパスワードを照合し終えた直後や、フィードのトークンの作り直しでセッションを確かめた直後に停止が走ると、
    その後に書き込まれる新しいパスワードやトークンで、止めたはずの利用者が使えるようになる
  - 停止とリセットは CLI から、Web サーバーとは別のプロセスで走る。Web サーバーの中の `Mutex<Db>` で処理を 1 つずつにしても、この順序は守れない。
    守れるのは SQLite のトランザクションだけ
  - そこで、これらの操作は、書き込むトランザクション（`BEGIN IMMEDIATE`：始めた時点で書き込みのロックを取り、ほかのプロセスの書き込みと重ならない）の中で、
    前提がまだ成り立つかを確かめてから書く。成り立たなければ何も書かず、ログインし直しを求める
    - ログイン：ログインの手順（上記）の 3.
    - 本人のパスワードの変更：要求のセッションがまだあり、照合に使ったパスワードのハッシュがまだ同じこと
    - フィードのトークンの作り直し：要求のセッションがまだあること
  - 停止とリセットも同じ種類のトランザクションで行う。どちらが先でも、後から走ったほうが先の結果を見て判定するので、止めた資格が戻ることはない
  - 認証の状態でない書き込み（評価・既読など）は、停止の直前に受けた要求が停止の後に書いても、資格は戻らないので、確かめ直さない
- **資格の失効は 1 つの操作にまとめる**
  - 利用者の認証の状態は、パスワード・セッション・フィードのトークンと、ログインの失敗の記録（回数と待ち時間）からなる。
    止めるときにどれかを消し忘れると、そこから読み続けられる（例えばパスワードだけ変えても、フィードの URL で記事を読める）。
    失敗の記録が残ると、リセットした直後でも待ち時間が続き、新しいパスワードでログインできない
  - そこで、これらをまとめて初期化する操作を `Db` に 1 つだけ置き、利用の停止とパスワードのリセットはどちらもこれを通す
    - 停止：すべて初期化する（パスワードは NULL）
    - リセット：同じトランザクションで、すべて初期化してから新しいパスワードを設定する。フィードの URL も変わるので、本人は設定画面で作り直す。
      リセットは漏れた疑いがあるときにも使うので、フィードのトークンだけ残すことはしない
  - IP ごとの失敗の回数（メモリ）は利用者に紐付かないので、ここでは消さない
  - 本人のパスワードの変更も、同じくパスワード以外をすべて消してから新しいパスワードを設定する。違いは、要求元に新しいセッションを発行することと、
    失敗の記録を初期化しないこと（今のパスワードの照合の失敗を数えているため。成功した変更では、ログインの成功と同じく 0 に戻す）
- **プロファイルの無い利用者の一覧**
  - 今の一覧（`Db::list_articles`）は、既定の表示で推薦点が最低点以上の記事だけを出す（`rows.rec >= :min`）。
    確認の枠は最低点未満の記事（`rows.rec < :min`）を出す。プロファイルが無いと採点が無く推薦点が NULL になり、どちらにも入らない。
    フィードも同じ一覧を使うので、所有者以外はホームもフィードも空になる
  - 「未採点」には、採点がまだ済んでいない記事と、プロファイルが無くて採点できない利用者の 2 つが混ざっている。
    前者を隠すのは今までどおり正しいが、後者で隠すと何も出ない
  - そこで、プロファイルが無い利用者（プロファイルのハッシュが NULL）のときは、推薦点での絞り込みを掛けない。
    評価 1〜2 と非軽水炉の記事を隠すのは今までどおりで、並びは新しい順にする。確認の枠は出さない（最低点未満という区別が無いため）
  - 最低点の今の決まり（`web::server::pages` の `list` と `web::html::ListView`）
    - 既定の一覧：`?min=N` が無ければ設定の `web.min_score`。`min=0` は「すべて」（評価 1〜2・非軽水炉・未採点も出す）の意味を兼ねる
    - 評価・ブックマークで絞った一覧：`?min=N` が無ければ 0（点数で絞らない）。検索（`Db::search_articles`）の `min_score` は `None` になり、
      未採点も出る。プロファイルの有無によらず、今のままで空にはならない
    - 正規の URL（`ListView::url`）は、最低点がその表示の既定（`min_default`）と同じなら `?min=` を付けない
  - 変えるのは既定の一覧の既定だけにする。最低点を `u8` の 1 つの値で持つ今の形では、プロファイルの無い利用者の既定（最低点なし）を表せない。
    「最低点なし」は `0`（すべて）とも、設定の値とも違う 3 つ目の状態で、`0` や設定の値に寄せると、どちらかの意味が失われる
    - `ListView` の最低点と既定を、`Option<u8>` にする。`None` は最低点なし（推薦点で絞らないが、評価 1〜2 と非軽水炉は隠す）、`Some(0)` は「すべて」、`Some(n)` は n 点以上
    - 既定の一覧の既定（`min_default`）は、プロファイルがあれば `Some(web.min_score)`、無ければ `None`。絞り込みの既定は今までどおり `Some(0)`
    - 正規の URL は今までどおり「既定と同じなら付けない」。プロファイルの無い利用者では、`/` は最低点なし、`/?min=50` は 50 点以上の明示で、
      別の URL・別の結果になる（`?min=50` が `/` に寄せられて条件が失われることはない）
    - `ListQuery` の最低点も `Option<u8>` にし、`None` なら推薦点で絞らない。`show_all` は `Some(0)` のときだけ
    - フィードと `/api/articles` の既定も、既定の一覧と同じ関数（プロファイルの有無から `min_default` を決める）で決める
  - プロファイルの無い利用者が自分で最低点を選んだとき（`?min=60` や検索の `min_score=60`）は、今までどおり未採点を除くので何も出ない。
    選んだ条件のとおりの結果で、採点ができれば出るようになる
  - プロファイルのある利用者（所有者）の振る舞いは変えない
  - 利用者ごとの点数（プロファイルと記事のトピックから出す）ができたら、この場合は無くなるか、プロファイルを登録する前の利用者だけになる

### 利用者を持つデータと処理の扱い

これまで利用者は所有者 1 人だったので、利用者を持つデータを「誰に見せるか」、処理を「誰の分を扱うか」を決めずに済んでいた。
複数の利用者にするにあたって、`user_id` を持つテーブルと、所有者に固定している処理（`Db::owner_id` の呼び出し）をすべて挙げ、扱いを決める。

本人だけが読み書きするもの（ほかの利用者からは見えない）：

| テーブル                        | 中身                     | 今の読み方         | この計画での変更                                                                 |
| ------------------------------- | ------------------------ | ------------------ | -------------------------------------------------------------------------------- |
| `ratings`・`reads`・`bookmarks` | 評価・既読・ブックマーク | 利用者で絞っている | 無し（利用者をセッションから引くだけ）                                           |
| `events`                        | 開いた記録               | 同上               | 同上                                                                             |
| `explore_picks`                 | 確認の枠に出した記事     | 同上               | 同上（プロファイルが無ければ確認の枠を出さない）                                 |
| `profiles`・`scores`            | 関心と採点               | 同上               | 無し。所有者以外の分は作られない（採点の計画で扱う）                             |
| `user_memberships`              | 自己申告の会員資格       | 同上               | 無し。新しい利用者は資格なしで、会員向けの本文は見えない。設定する手段は作らない |
| `translation_requests`          | 和訳の依頼の印           | 同上               | 印は本人の分。処理は下の「処理」を参照                                           |

本人の分とほかの人の一部が見えるもの：

| テーブル   | 見える範囲                                     | この計画での変更                                           |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------- |
| `comments` | 自分のものと、ほかの人の公開（`public`）のもの | 無し（`Db::comments` がすでにそう絞っている）              |
| `reports`  | 一般の利用者は自分のもの、管理者は全件         | 出した人で絞る指定を足す（上の「管理者だけができること」） |

全員で共有するもの（`user_id` を持たない）：記事・本文・要約や和訳などの成果物・トピック・訳語集・報道のグループ。閲覧の制限は会員資格（`artifact_access` など）だけで決まり、この計画では変えない。

処理（所有者に固定しているもの）：

| 処理                                                                   | 今                                          | この計画での扱い                                                                                                     |
| ---------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 採点（`pipeline::run` の採点、`Db::profile_hash(owner)` による予約）   | 所有者のプロファイルだけ                    | 変えない（採点の計画で扱う）                                                                                         |

| 作り直し（`redo`）・CLI の `search`・`profile`・`eval`・`suggest`・MCP | 所有者                                      | 変えない。稼働ホストの利用者が使うもの                                                                               |
| Web のハンドラ（`viewer()`）                                           | 所有者                                      | セッションの利用者にする                                                                                             |

## 変更

1. マイグレーション `0031_login.sql`
   - `users` に `password_hash TEXT`（NULL ならログインできない）、`failed_logins INTEGER NOT NULL DEFAULT 0`、`locked_until TEXT`、`feed_token TEXT` を足す。
     `feed_token` の一意性は、別に一意の索引（`CREATE UNIQUE INDEX users_by_feed_token ON users (feed_token)`）で付ける。
     SQLite の `ALTER TABLE ... ADD COLUMN` は `UNIQUE` 付きの列を足せない（`Cannot add a UNIQUE column`）ため。NULL は一意の索引でも重複してよい
   - `sessions (token TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users (id) ON DELETE CASCADE, created_at TEXT NOT NULL, expires_at TEXT NOT NULL)` と、`user_id` の索引
   - 既存の所有者の行（`login = 'owner'`）はパスワードが NULL のまま。管理者が CLI でパスワードとログイン ID を設定するまでログインできない
2. `Db` の操作：パスワードの設定・照合（失敗の回数と待ち時間を含む）、セッションの作成（期限切れの行をまとめて消す）・引き当て（期限切れは無効）・削除、
   フィードのトークンの作成・引き当て、資格の失効
3. 一覧：`ListView` と `ListQuery` の最低点を `Option<u8>` にし、既定の一覧の既定をプロファイルの有無で決める（無ければ `None`）。
   フィードと JSON API の既定も同じ関数で決める。絞り込みの既定（`Some(0)`）は変えない。フィードの `atom()` は self のリンクの URL を受け取る
4. サーバー：接続元のアドレスをハンドラに渡す（`into_make_service_with_connect_info::<SocketAddr>()`）。テスト用のサーバーも同じ
5. CLI `nucrawler user`
   - `user add <login> <表示名>`：利用者を作り、初期パスワードを作って 1 回だけ表示する
   - `user reset-password <login>`：資格をすべて失効させ、新しいパスワードを作って表示する
   - `user disable <login>`：資格をすべて失効させる。戻すときは `reset-password`
   - `user rename <login> <新しい login>`：所有者の `owner` をメールアドレスに変えるときなどに使う
   - `user list`：login・表示名・管理者か・パスワードが設定済みか
   - 利用者の削除は作らない（星・既読などの記録ごと消えるため。必要になったら足す）。止めるときは `disable`
6. Web
   - `/login`（GET：画面、POST：照合してセッションを作る）、`/logout`（POST）、`/settings/password`（POST）、`/settings/feed-token`（POST）
   - `viewer()` をやめ、セッションから利用者を引く extractor（例えば `Viewer { user, is_admin }`）に置き換える。プロファイルのハッシュは、使うハンドラで引く
   - 管理者だけの操作は、extractor の `is_admin` を見て 403 を返す。訳語集と指摘の画面は `is_admin` で管理用のフォームを出し分ける
   - 画面のヘッダーにログイン中の表示名とログアウトを出す。設定画面に、パスワードの変更と、フィードの URL を出す
7. 指摘：`Db::reports` に出した人で絞る指定を足す。受付箱（`/reports`）は管理者だけ。詳細の画面では、一般の利用者には自分の指摘だけを出す。設定画面の受付中の件数は管理者だけ
8. 画面の共通の部分：`Page` を利用者から作る関数を 1 つにし、運用の警告は管理者のときだけ読む。すべての画面がこの関数を通す
9. 和訳の依頼：`Db::pending_translate` が、誰の依頼でも拾う（未完了の依頼のうち最も古い依頼の時刻で並べる）
10. README の「認証は無いので…」を、認証の説明と「HTTP で待ち受けるので社内 LAN 内だけで使う」に書き換え、`user` の CLI を足す

## やらないこと

- HTTPS（証明書を用意できないため。Context を参照）
- 自分で登録する機能、メールでのリセット、二要素認証
- Entra ID などの OIDC
- 受け付ける Host の制限（設定に並べた Host 以外を断る）。Origin の確認・戻り先の基準・フィードの URL は、今までどおり要求の `Host` ヘッダーを使う。
  `Host` は送り手が書ける値で、DNS rebinding（相手が自分のドメインの名前を nucrawler の LAN 内の IP に向ける）では `Host` も `Origin` もそのドメインになり、
  Origin の確認を通る。それでも制限しないのは、この環境では実害が小さく、手間が大きいため
  - Cookie は発行したホスト名にしか送られないので、利用者がいつもの URL でログインしたセッションは、相手のドメインのページには渡らない
  - 相手が得をするのは、利用者が相手のドメインの URL を開き、そこに出た（本物の）ログイン画面でログインしたときだけ。
    このときセッションの Cookie は相手のドメインに付き、名前を相手のサーバーに戻した後で、相手に送られる（LAN の盗聴は要らない）。
    ただ、同じ前提（利用者が相手のドメインでログインする）が成り立つなら、相手は nucrawler を使わずに偽のログイン画面を置くだけで、
    セッションより強いパスワードそのものを取れる。Host を制限しても、相手が取れる手段は減らない
  - 要求の `Host` を偽っても、それで変わる応答（戻り先・フィードのリンク）は、その要求を送った人にだけ返る。間にキャッシュもリバースプロキシも無いので、
    偽の値を含む応答がほかの利用者に配られることはない。これは応答の広がりの話で、上の経路でセッションを取られた場合の影響とは別。
    取られたセッションでは相手が本人として操作でき、管理者のセッションなら共有の訳語集も変えられる。その経路の前提は上のとおりフィッシングと同じなので、
    防ぐのは Host の制限ではなく、利用者がいつもの URL 以外でログインしないこと
  - HTTP のままにすると決めたので、パスワードと Cookie は LAN に平文で流れる。これに比べて rebinding の危険は小さく、ここだけ厳しくしても全体の守りは変わらない
  - 一方、許可する Host を必須の設定にすると、アクセスに使う名前やアドレスが変わるたびに設定を直す必要があり、忘れると全員が使えなくなる
  - 普通の他サイトからの送信（CSRF）は、Origin と Host の一致の確認で今までどおり防げる
- 利用者ごとの採点とプロファイルの編集。所有者以外の一覧は、上の「プロファイルの無い利用者の一覧」のとおり新しい順になる。
  プロファイルと記事のトピックからアルゴリズムで点数を出すことを、別の計画で扱う
- 和訳の依頼の制限。誰が依頼しても所有者の LLM の枠を使う（依頼を拾う変更は「変更」の 9.）。人数が少ないうちは制限しない
- JSON API のトークンでのアクセス。今は画面の JavaScript がブラウザの Cookie で使うだけなので、ほかから使う必要が出たら足す
- MCP と CLI の `search` などは、稼働ホストの利用者が使うものなので、今までどおり所有者として動かす

## テスト

- パスワードはハッシュで保存され、正しいパスワードでだけ照合に通る。パスワードが NULL の利用者はログインできない
- パスワードの条件：11 文字は 400、12 文字は通る。1024 バイトは通り、1025 バイトは 400。初期パスワードは条件を満たす
- ID ごとの待ち時間：5 回目の失敗までは待たない。6 回目で 1 分、7 回目で 2 分、10 回目で 15 分、11 回目も 15 分。
  待ち時間中は正しいパスワードでも通らず、待ち時間中の試行は回数も `locked_until` も変えない。待ち時間が過ぎて成功すると回数が 0 に戻る
- IP ごとの待ち時間：20 回目の失敗までは待たず、21 回目から 15 分待つ。待ち時間中の試行は数えず、待ち時間は延びない。最後の失敗から 15 分過ぎると数え直す
- 同じ IP から、存在しない ID を変えながら続けて失敗すると、その IP は待たされる。ほかの IP からは待たされない。
  同じ IP で接続元のポートが違う（接続し直した）失敗も、同じ回数に数えられる。
  IP は接続元のアドレスで決まり、`X-Forwarded-For` を付けても変わらない（IP ごとの数え方はメモリの型の単体テストで、複数の IP を与えて確かめる）
- ID が無い・パスワードが違う・ID ごとの待ち時間中・パスワードが NULL の応答は、状態コードも本文も同じで、どれも照合を 1 回行う（照合の回数で確かめる）
- 照合の後、書き込みの前にリセット・停止があると、古いパスワードで照合が通っていてもセッションは作られない
  （1. と 2. の後に状態を変えてから 3. を呼ぶ形で、手順を段階ごとに呼べるようにして確かめる）
- 本人のパスワードの変更で、照合の後・書き込みの前に停止があると、新しいパスワードは書かれず、パスワードは NULL のまま
- フィードのトークンの作り直しで、セッションを確かめた後・書き込みの前に停止があると、新しいトークンは書かれない
- IP ごとの失敗の記録：最後の失敗から 15 分過ぎた項目は消える。上限を超える数の IP で失敗しても、項目の数は上限を超えない
- IP ごとの失敗の回数は、同じ IP からのログインの成功では消えない（ほかの ID での失敗と自分の ID での成功を繰り返しても、IP は待たされる）
- 1024 バイトを超えるパスワードでのログインは、計算せずに失敗の共通の応答になり、IP ごとの失敗に数えられる。パスワードの変更では、今・新しいのどちらが超えても 400
- パスワードの変更の計算も、ログインの照合と同じ同時実行数の上限に数えられる（空きが無ければ 503）
- 照合を始めた後に接続を切ったログインも、IP ごと・ID ごとの失敗に数えられる（照合の中で待つ仕掛けを入れたテストで、要求を捨ててから記録を確かめる）
- ID ごとの回数は 10 で止まり、10 回目の後に何度失敗しても待ち時間は 15 分のまま（回数を 10 にした状態から失敗させて確かめる）。IP ごとの回数は 21 で止まる
- 照合の空きが無いときの要求は、待たずに 503 になり、IP ごとの失敗には数えない。要求が途中で切られても、許可は計算が終わるまで返らない
- ログインの応答の Cookie は `HttpOnly`・`SameSite=Lax`・`Path=/`・`Max-Age` 30 日を持ち、`Secure` を持たない（HTTP なので、付けるとブラウザが送らない）。
  パスワードの変更で差し替える Cookie も同じ。ログアウトの応答は、同じ `Path` で `Max-Age=0`
- セッション：期限切れのトークンでは利用者が引けない。ログアウトで消える。ログインでセッションを作ると、ほかの利用者の期限切れの行も消える
- 失効：停止とリセットの後は、古いパスワード・セッション・フィードのトークンのどれでも読めない
- 本人のパスワードの変更：変更前の Cookie（要求元のものも含む）はどれも 401 になり、応答で差し替えた新しい Cookie では読める。変更前のフィードのトークンは 401
- パスワードの変更の今のパスワードの誤り：ID ごとの失敗に数えられ、6 回目でその人のセッションがすべて消える（要求元の Cookie も 401）。
  待ち時間中は、正しい今のパスワードでも変更できない
- 待ち時間中の利用者をリセットすると、新しいパスワードですぐにログインでき、失敗の回数も 0 に戻っている
- 未ログインの GET はログイン画面に回り、ログイン後に元のパス（クエリを含む）へ戻る
- 戻り先 `next` がほかのホストを指すときは、自分のホストの `/` に戻る。リダイレクト先はいつも自分のホストの絶対 URL。確かめる値：
  - `//evil.example`、`http://evil.example/`
  - `/\evil.example`（クエリでは `next=%2F%5Cevil.example` と送られ、デコードするとこの値になる）
  - `/`・タブ・`/evil.example`（ブラウザはタブを無視するので `//evil.example` になる）
- 未ログインの POST と `/api/...` は 401
- 他サイトの Origin からの `/login`・`/logout`・`/settings/password`・`/settings/feed-token` への POST は 403 で、
  セッションが作られず、消えず、パスワードとフィードのトークンも変わらない
- 2 人の利用者が同じ記事に付けた星・既読・ブックマークが、互いの画面に出ない
- フィード：トークンの利用者の既読で絞られる。トークンが無い・違うと 401。作り直すと古いトークンは 401。self のリンクはトークンを含む購読用の URL
- プロファイルの無い利用者：一覧とフィードに、評価 1〜2 と非軽水炉を除いた記事が新しい順に出る。確認の枠は出ない。所有者の一覧は変わらない
- 指摘：一般の利用者の `/reports` の GET は 403。詳細の画面には自分の指摘だけが出て、ほかの人の指摘（`note`・`reply` を含む）は出ない。
  設定画面に受付中の件数が出ない。管理者にはすべて出る
- 和訳の依頼：所有者以外が依頼した記事も、和訳のステージで拾われ、和訳ができると依頼が閉じる
- プロファイルの無い利用者：評価（`rating=4` など）やブックマークで絞った一覧に、該当する記事が出る。`?min=60` を選ぶと未採点なので出ない
- プロファイルの無い利用者：`/` は最低点なし（評価 1〜2・非軽水炉は隠れ、未採点は出る）、`/?min=0` はすべて、`/?min=50` は未採点が出ない。
  3 つとも正規の URL がそのまま残る（`/?min=50` が `/` に寄せられない）
- 所有者（プロファイルあり）の回帰：`/` は設定の最低点、`/?rating=4` と `/?bookmarked=1` は最低点で絞らず低い点・未採点の記事も出る、正規の URL は今と同じ
- 管理者でない利用者の訳語集の編集と指摘の処理は 403、管理者は通る
- 管理者でない利用者の訳語集と指摘の画面には、編集・削除・対応のフォームが出ない。管理者の画面には出る
- 運用の警告（取得の失敗など）がある状態で、管理者でない利用者のどの画面（一覧・詳細・検索・設定・訳語集）にも警告が出ない。管理者の画面には出る
- 既存の Web のテストは、テスト用の利用者でログインした状態で通す（`test_support` にログイン済みの Cookie を付ける手段を足す）
