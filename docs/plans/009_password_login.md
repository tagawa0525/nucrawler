# ログイン ID とパスワードでの認証

## Context

これまで nucrawler はオーナー 1 人で使っていて、Web UI に認証は無い。
Tailscale の tailnet のアドレスで待ち受けて、ネットワークに入れる人を利用者とみなしてきた（README の「認証は無いので、Tailscale など信頼できるネットワークのアドレスで待ち受ける」）。

これを社内 LAN 内の複数の人に使ってもらう。条件は次のとおり。

- 使うのは社内 LAN の中だけ。インターネットには出さない
- 社内には Entra ID があるが、nucrawler の開発・稼働環境（個人の環境）からは使えない
- リバースプロキシは置かない。nucrawler が直接待ち受ける
- **HTTP のまま**にする（社内 CA などで証明書を用意できないため）。パスワードとセッションの Cookie は LAN に平文で流れる。
  これを承知のうえで「社内 LAN 内だけ」を前提とする

### DB はもう利用者ごと、Web は所有者に固定

星（`ratings`）・既読（`reads`）・ブックマーク（`bookmarks`）・開いた記録（`events`）・プロファイル（`profiles`）・採点（`scores`）・コメント・指摘は、
どれもキーに `user_id` を持っていて、利用者ごとに記録できる。`users.login` には「Tailscale-User-Login」と注記があり、利用者を見分ける列として用意してある。

一方、Web のハンドラは、利用者をいつも所有者（`users.is_owner = 1` の 1 行）にしている。

```rust
/// 利用者（今は所有者だけ）と、現在のプロファイルのハッシュ。
fn viewer(db: &Db) -> Result<(i64, Option<String>), DbError> {
    let user = db.owner_id()?;
    let hash = db.profile_hash(user)?;
    Ok((user, hash))
}
```

`src/web/server` のハンドラは、この `viewer()` を通して利用者を決めている（約 20 か所）。
そのため、誰がアクセスしても、所有者の星・既読・ブックマークを読み書きしてしまう。

## 方針

- 認証の方式は **ログイン ID（メールアドレス）とパスワード**
  - Entra ID（OIDC）は使えず、リバースプロキシに認証を任せることもできないので、アプリで持つ
  - `users.login` をログイン ID にする。将来 Entra ID に移るときも、この列を利用者の一意な値として使い続ければ、
    星・既読などのデータはそのまま残せる。今は OIDC を見越した抽象化は作らない
- **アカウントは管理者が CLI で発行する**
  - 自分で登録する機能は作らない
  - メールでのパスワードのリセットも作らない（メールの送信の仕組みが要らなくなる）。忘れたら管理者が CLI でリセットする
  - 管理者は所有者（`is_owner = 1`）。CLI は稼働ホストに入れる人しか使えないので、CLI の操作自体が管理者の確認を兼ねる
- **パスワードは argon2id でハッシュにして保存する**（`argon2` crate を足す）
  - 標準ライブラリにはパスワードのハッシュ関数も安全な乱数も無く、自作は危ないので、依存を足す理由がある
  - セッションのトークンの乱数も、この crate が使う OS の乱数（`OsRng`）から作る
- **セッションは DB に持つ**
  - ログインしたら 256 bit の乱数のトークンを作り、Cookie に入れ、`sessions` に保存する
  - トークンは DB に平文で置く。ハッシュにするには別の依存（SHA-256 など）が要る一方、DB を読めるのは稼働ホストに入れる管理者だけで、
    DB を読めればトークンが無くても記事も印もすべて読めるため
  - 有効期限はログインから 30 日。ログアウトで行を消す
  - 期限切れの行は、ログインでセッションを作るときに、全員の分をまとめて消す。古いトークンが再び送られるのを待つだけでは、
    捨てられた Cookie の行がいつまでも残るため。ログインの頻度は低く、消す行も少ないので、ここで消しても重くならない
  - Cookie は `HttpOnly`・`SameSite=Lax`・`Path=/`。HTTP なので `Secure` は付けられない
  - `SameSite=Strict` にしない理由：フィードリーダーやチャットのリンクから詳細を開くと、Strict では Cookie が送られず毎回ログイン画面になる。
    書き込み（POST）は、今もある Origin と Host の一致の確認（`AppError::CrossSite`）で他サイトからの送信を防いでいるので、Lax で足りる
  - Cookie の読み書きは `Cookie` / `Set-Cookie` ヘッダーを直接扱う（1 つの値を読むだけなので、`axum-extra` などは足さない）
- **パスワードの条件**
  - 本人が決めるパスワードは 12 文字以上、1024 バイト以下。満たさなければ 400 で、設定画面に理由を出す
  - 上限は、極端に長い入力でハッシュの計算を重くされないため。文字の種類の条件（大文字・記号など）は付けない。
    長さのほうが強さに効き、種類の条件は覚えにくいパスワードを生むだけのため
  - CLI が作る初期パスワードは、紛らわしい文字（`0` `O` `1` `l` `I`）を除いた英数字 20 文字（約 110 bit）。条件と同じ上限・下限の中に収まる
  - ログイン ID も 254 バイト（メールアドレスの上限）以下に限る
- **総当たり対策**
  - ログイン ID ごとに続けて失敗した回数を持ち、5 回を超えたら、次に試せるまで待たせる（失敗が続くほど長く、上限 15 分）。成功したら数え直す
  - ID ごとの回数は `users` の行に持つので、存在しない ID には効かない。ID を変えながら試す相手には、送り元の IP ごとの制限で対処する。
    リバースプロキシが無く、接続元の IP がそのまま利用者の端末なので、IP で数えられる。回数はメモリに持つ（再起動で消えてよい）
  - 1 回の照合（argon2id）は重いので、同時に計算するのは 2 つまでにする（セマフォ）。IP を変えられても、CPU を使い切られない。
    照合は DB のロックの外で行い、ほかの要求を待たせない
  - 失敗の応答はすべて同じにする。ID が無い、パスワードが違う、待ち時間中、パスワードが NULL のどれでも、
    同じ文言（「ログイン ID かパスワードが違うか、失敗が続いたため今はログインできません」）と同じ状態コードを返す。
    ID が無いときやパスワードが NULL のときも、ダミーのハッシュに対して照合を 1 回行い、応答までの時間を揃える。
    これで、応答の違いや時間から、どの ID が存在するかを調べられない
- **ログインしていない要求**
  - 画面（GET）はログイン画面に回し、ログイン後に元の画面へ戻す。戻り先は `next` の値で受け取る
  - `next` は利用者が書き換えられるので、他サイトへ飛ばす（オープンリダイレクト）のに使われないようにする。
    文字列の形（`/` で始まる、`//` で始まらない）で判定すると、ブラウザの URL の解釈とずれる。
    例えば `/\evil.example` はブラウザでは `http://evil.example/` になり、フォームで `%5C` と送っても同じになる。
    そこで、ブラウザと同じ規則（WHATWG URL）で解釈する `url` crate（既存の依存）を使う
    - `http://{Host ヘッダー}/` を基準に `next` を解釈し、結果のスキーム・ホスト・ポートが基準と同じときだけ使う。違えば `/` に戻す
    - リダイレクト先は、解釈した結果の絶対 URL にする。パスだけを返すと、解釈で `//evil.example` のようなパスになったときに、
      ブラウザがまた別のホストとして読んでしまうため。絶対 URL ならホストが決まっていて、読み違いが起きない
  - ログインとログアウトの POST にも、ほかの POST と同じ Origin と Host の一致の確認を掛ける（他サイトから別のアカウントでログインさせられるのを防ぐ）
  - JSON API（`/api/...`）と POST は 401 を返す。画面の JavaScript が使う `/api/marks` などはブラウザの Cookie で通る
- **フィード（`/feed.xml`）は利用者ごとのトークンで読む**
  - フィードリーダーはログインできないので、Cookie の代わりに URL のトークン（`/feed.xml?token=...`）で利用者を決める
  - トークンは `users.feed_token` に持ち、設定画面に購読用の URL を出す。作り直すと古い URL は使えなくなる
  - トークンの無いアクセスは 401
  - Atom の `rel="self"` のリンクは、今は `{base}/feed.xml` に固定している（`web::feed::atom`）。このままだとフィード自身が示す URL が 401 になり、
    それを使って購読し直すリーダーで読めなくなる。そこで `atom()` に、トークンを含めた購読用の URL を渡し、self のリンクにする
- **管理者だけができること**：訳語集の編集（`/glossary` への POST）と、指摘の処理（`/reports/{id}`）
  - 訳語集は全員の和訳に効く共有のデータで、和訳は所有者の LLM の枠で作るため
  - 指摘を出すこと・訳語集を見ることは全員ができる
  - 管理者でなければ 403
  - 画面にも出し分ける。今の `glossary_page` と `reports_page` は、編集・削除・対応のフォームをいつも出している。
    ハンドラで 403 を返すだけだと、一般の利用者には押すと必ず失敗するフォームが並ぶ。描画に `is_admin` を渡し、管理者でなければ管理用のフォームを出さない
- **パスワードの変更**は、本人が設定画面から行う（今のパスワードと新しいパスワードを入れる）。変えたら、その人のほかのセッションは消す
- **資格の失効は 1 つの操作にまとめる**
  - 利用者の認証の状態は、パスワード・セッション・フィードのトークンと、ログインの失敗の記録（回数と待ち時間）からなる。
    止めるときにどれかを消し忘れると、そこから読み続けられる（例えばパスワードだけ変えても、フィードの URL で記事を読める）。
    失敗の記録が残ると、リセットした直後でも待ち時間が続き、新しいパスワードでログインできない
  - そこで、これらをまとめて初期化する操作を `Db` に 1 つだけ置き、利用の停止とパスワードのリセットはどちらもこれを通す
    - 停止：すべて初期化する（パスワードは NULL）
    - リセット：同じトランザクションで、すべて初期化してから新しいパスワードを設定する。フィードの URL も変わるので、本人は設定画面で作り直す。
      リセットは漏れた疑いがあるときにも使うので、フィードのトークンだけ残すことはしない
  - IP ごとの失敗の回数（メモリ）は利用者に紐付かないので、ここでは消さない
  - 本人のパスワードの変更では、フィードのトークンは残す（本人の操作で、URL が変わると購読し直しになるため）。漏れた疑いがあれば、本人が設定画面で作り直せる
- **プロファイルの無い利用者の一覧**
  - 今の一覧（`Db::list_articles`）は、既定の表示で推薦点が最低点以上の記事だけを出す（`rows.rec >= :min`）。
    確認の枠は最低点未満の記事（`rows.rec < :min`）を出す。プロファイルが無いと採点が無く推薦点が NULL になり、どちらにも入らない。
    フィードも同じ一覧を使うので、所有者以外はホームもフィードも空になる
  - 「未採点」には、採点がまだ済んでいない記事と、プロファイルが無くて採点できない利用者の 2 つが混ざっている。
    前者を隠すのは今までどおり正しいが、後者で隠すと何も出ない
  - そこで、プロファイルが無い利用者（プロファイルのハッシュが NULL）のときは、推薦点での絞り込みを掛けない。
    評価 1〜2 と非軽水炉の記事を隠すのは今までどおりで、並びは新しい順にする。確認の枠は出さない（最低点未満という区別が無いため）
  - プロファイルのある利用者（所有者）の振る舞いは変えない
  - 利用者ごとの点数（プロファイルと記事のトピックから出す）ができたら、この場合は無くなるか、プロファイルを登録する前の利用者だけになる

## 変更

1. マイグレーション `0031_login.sql`
   - `users` に `password_hash TEXT`（NULL ならログインできない）、`failed_logins INTEGER NOT NULL DEFAULT 0`、`locked_until TEXT`、`feed_token TEXT UNIQUE` を足す
   - `sessions (token TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users (id) ON DELETE CASCADE, created_at TEXT NOT NULL, expires_at TEXT NOT NULL)` と、`user_id` の索引
   - 既存の所有者の行（`login = 'owner'`）はパスワードが NULL のまま。管理者が CLI でパスワードとログイン ID を設定するまでログインできない
2. `Db` の操作：パスワードの設定・照合（失敗の回数と待ち時間を含む）、セッションの作成（期限切れの行をまとめて消す）・引き当て（期限切れは無効）・削除、
   フィードのトークンの作成・引き当て、資格の失効
3. 一覧：プロファイルのハッシュが NULL のときは推薦点で絞らず、新しい順に並べる。フィードの `atom()` は self のリンクの URL を受け取る
4. CLI `nucrawler user`
   - `user add <login> <表示名>`：利用者を作り、初期パスワードを作って 1 回だけ表示する
   - `user reset-password <login>`：資格をすべて失効させ、新しいパスワードを作って表示する
   - `user disable <login>`：資格をすべて失効させる。戻すときは `reset-password`
   - `user rename <login> <新しい login>`：所有者の `owner` をメールアドレスに変えるときなどに使う
   - `user list`：login・表示名・管理者か・パスワードが設定済みか
   - 利用者の削除は作らない（星・既読などの記録ごと消えるため。必要になったら足す）。止めるときは `disable`
5. Web
   - `/login`（GET：画面、POST：照合してセッションを作る）、`/logout`（POST）、`/settings/password`（POST）、`/settings/feed-token`（POST）
   - `viewer()` をやめ、セッションから利用者を引く extractor（例えば `Viewer { user, is_admin }`）に置き換える。プロファイルのハッシュは、使うハンドラで引く
   - 管理者だけの操作は、extractor の `is_admin` を見て 403 を返す。訳語集と指摘の画面は `is_admin` で管理用のフォームを出し分ける
   - 画面のヘッダーにログイン中の表示名とログアウトを出す。設定画面に、パスワードの変更と、フィードの URL を出す
6. README の「認証は無いので…」を、認証の説明と「HTTP で待ち受けるので社内 LAN 内だけで使う」に書き換え、`user` の CLI を足す

## やらないこと

- HTTPS（証明書を用意できないため。Context を参照）
- 自分で登録する機能、メールでのリセット、二要素認証
- Entra ID などの OIDC
- 利用者ごとの採点とプロファイルの編集。所有者以外の一覧は、上の「プロファイルの無い利用者の一覧」のとおり新しい順になる。
  プロファイルと記事のトピックからアルゴリズムで点数を出すことを、別の計画で扱う
- 和訳の依頼の制限。誰が依頼しても所有者の LLM の枠を使う。人数が少ないうちは制限しない
- JSON API のトークンでのアクセス。今は画面の JavaScript がブラウザの Cookie で使うだけなので、ほかから使う必要が出たら足す
- MCP と CLI の `search` などは、稼働ホストの利用者が使うものなので、今までどおり所有者として動かす

## テスト

- パスワードはハッシュで保存され、正しいパスワードでだけ照合に通る。パスワードが NULL の利用者はログインできない
- パスワードの条件：11 文字は 400、12 文字は通る。1024 バイトは通り、1025 バイトは 400。初期パスワードは条件を満たす
- 失敗が続くと待ち時間の間は正しいパスワードでも通らず、成功すると失敗の回数が戻る
- 同じ IP から、存在しない ID を変えながら続けて失敗すると、その IP は待たされる
- ID が無い・パスワードが違う・待ち時間中・パスワードが NULL の応答は、状態コードも本文も同じ。ID が無いときも照合を行う（照合の回数で確かめる）
- セッション：期限切れのトークンでは利用者が引けない。ログアウトで消える。ログインでセッションを作ると、ほかの利用者の期限切れの行も消える
- 失効：停止とリセットの後は、古いパスワード・セッション・フィードのトークンのどれでも読めない。本人のパスワードの変更では、ほかのセッションは消え、フィードのトークンは残る
- 待ち時間中の利用者をリセットすると、新しいパスワードですぐにログインでき、失敗の回数も 0 に戻っている
- 未ログインの GET はログイン画面に回り、ログイン後に元のパス（クエリを含む）へ戻る
- 戻り先 `next` がほかのホストを指すときは、自分のホストの `/` に戻る。リダイレクト先はいつも自分のホストの絶対 URL。確かめる値：
  - `//evil.example`、`http://evil.example/`
  - `/\evil.example`（クエリでは `next=%2F%5Cevil.example` と送られ、デコードするとこの値になる）
  - `/`・タブ・`/evil.example`（ブラウザはタブを無視するので `//evil.example` になる）
- 未ログインの POST と `/api/...` は 401
- 他サイトの Origin からの `/login`・`/logout`・`/settings/password`・`/settings/feed-token` への POST は 403 で、
  セッションが作られず、消えず、パスワードとフィードのトークンも変わらない
- 2 人の利用者が同じ記事に付けた星・既読・ブックマークが、互いの画面に出ない
- フィード：トークンの利用者の既読で絞られる。トークンが無い・違うと 401。作り直すと古いトークンは 401。self のリンクはトークンを含む購読用の URL
- プロファイルの無い利用者：一覧とフィードに、評価 1〜2 と非軽水炉を除いた記事が新しい順に出る。確認の枠は出ない。所有者の一覧は変わらない
- 管理者でない利用者の訳語集の編集と指摘の処理は 403、管理者は通る
- 管理者でない利用者の訳語集と指摘の画面には、編集・削除・対応のフォームが出ない。管理者の画面には出る
- 既存の Web のテストは、テスト用の利用者でログインした状態で通す（`test_support` にログイン済みの Cookie を付ける手段を足す）
