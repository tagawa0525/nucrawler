# ログイン ID とパスワードでの認証

## Context

これまで nucrawler はオーナー 1 人で使っていて、Web UI に認証は無い。
Tailscale の tailnet のアドレスで待ち受けて、ネットワークに入れる人を利用者とみなしてきた（README の「認証は無いので、Tailscale など信頼できるネットワークのアドレスで待ち受ける」）。

これを社内 LAN 内の複数の人に使ってもらう。条件は次のとおり。

- 使うのは社内 LAN の中だけ。インターネットには出さない
- 社内には Entra ID があるが、nucrawler の開発・稼働環境（個人の環境）からは使えない
- リバースプロキシは置かない。nucrawler が直接待ち受ける
- **HTTP のまま**にする（社内 CA などで証明書を用意できないため）。パスワードとセッションの Cookie は LAN に平文で流れる。
  これを承知のうえで「社内 LAN 内だけ」を前提とする

### DB はもう利用者ごと、Web は所有者に固定

星（`ratings`）・既読（`reads`）・ブックマーク（`bookmarks`）・開いた記録（`events`）・プロファイル（`profiles`）・採点（`scores`）・コメント・指摘は、
どれもキーに `user_id` を持っていて、利用者ごとに記録できる。`users.login` には「Tailscale-User-Login」と注記があり、利用者を見分ける列として用意してある。

一方、Web のハンドラは、利用者をいつも所有者（`users.is_owner = 1` の 1 行）にしている。

```rust
/// 利用者（今は所有者だけ）と、現在のプロファイルのハッシュ。
fn viewer(db: &Db) -> Result<(i64, Option<String>), DbError> {
    let user = db.owner_id()?;
    let hash = db.profile_hash(user)?;
    Ok((user, hash))
}
```

`src/web/server` のハンドラは、この `viewer()` を通して利用者を決めている（約 20 か所）。
そのため、誰がアクセスしても、所有者の星・既読・ブックマークを読み書きしてしまう。

## 方針

- 認証の方式は **ログイン ID（メールアドレス）とパスワード**
  - Entra ID（OIDC）は使えず、リバースプロキシに認証を任せることもできないので、アプリで持つ
  - `users.login` をログイン ID にする。将来 Entra ID に移るときも、この列を利用者の一意な値として使い続ければ、
    星・既読などのデータはそのまま残せる。今は OIDC を見越した抽象化は作らない
- **アカウントは管理者が CLI で発行する**
  - 自分で登録する機能は作らない
  - メールでのパスワードのリセットも作らない（メールの送信の仕組みが要らなくなる）。忘れたら管理者が CLI でリセットする
  - 管理者は所有者（`is_owner = 1`）。CLI は稼働ホストに入れる人しか使えないので、CLI の操作自体が管理者の確認を兼ねる
- **パスワードは argon2id でハッシュにして保存する**（`argon2` crate を足す）
  - 標準ライブラリにはパスワードのハッシュ関数も安全な乱数も無く、自作は危ないので、依存を足す理由がある
  - セッションのトークンの乱数も、この crate が使う OS の乱数（`OsRng`）から作る
- **セッションは DB に持つ**
  - ログインしたら 256 bit の乱数のトークンを作り、Cookie に入れ、`sessions` に保存する
  - トークンは DB に平文で置く。ハッシュにするには別の依存（SHA-256 など）が要る一方、DB を読めるのは稼働ホストに入れる管理者だけで、
    DB を読めればトークンが無くても記事も印もすべて読めるため
  - 有効期限はログインから 30 日。ログアウトで行を消す
  - Cookie は `HttpOnly`・`SameSite=Lax`・`Path=/`。HTTP なので `Secure` は付けられない
  - `SameSite=Strict` にしない理由：フィードリーダーやチャットのリンクから詳細を開くと、Strict では Cookie が送られず毎回ログイン画面になる。
    書き込み（POST）は、今もある Origin と Host の一致の確認（`AppError::CrossSite`）で他サイトからの送信を防いでいるので、Lax で足りる
  - Cookie の読み書きは `Cookie` / `Set-Cookie` ヘッダーを直接扱う（1 つの値を読むだけなので、`axum-extra` などは足さない）
- **総当たり対策**：ログイン ID ごとに続けて失敗した回数を持ち、5 回を超えたら、次に試せるまで待たせる（失敗が続くほど長く、上限 15 分）。
  成功したら数え直す。LAN 内の少人数なので、IP ごとの制限はしない
- **ログインしていない要求**
  - 画面（GET）はログイン画面に回し、ログイン後に元の画面へ戻す。戻り先は `/` で始まるパスだけを受け付ける（`//` で始まるものは他サイトに出るので拒否）
  - JSON API（`/api/...`）と POST は 401 を返す。画面の JavaScript が使う `/api/marks` などはブラウザの Cookie で通る
- **フィード（`/feed.xml`）は利用者ごとのトークンで読む**
  - フィードリーダーはログインできないので、Cookie の代わりに URL のトークン（`/feed.xml?token=...`）で利用者を決める
  - トークンは `users.feed_token` に持ち、設定画面に購読用の URL を出す。作り直すと古い URL は使えなくなる
  - トークンの無いアクセスは 401
- **管理者だけができること**：訳語集の編集（`/glossary` への POST）と、指摘の処理（`/reports/{id}`）
  - 訳語集は全員の和訳に効く共有のデータで、和訳は所有者の LLM の枠で作るため
  - 指摘を出すこと・訳語集を見ることは全員ができる
  - 管理者でなければ 403
- **パスワードの変更**は、本人が設定画面から行う（今のパスワードと新しいパスワードを入れる）。変えたら、その人のほかのセッションは消す

## 変更

1. マイグレーション `0031_login.sql`
   - `users` に `password_hash TEXT`（NULL ならログインできない）、`failed_logins INTEGER NOT NULL DEFAULT 0`、`locked_until TEXT`、`feed_token TEXT UNIQUE` を足す
   - `sessions (token TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users (id) ON DELETE CASCADE, created_at TEXT NOT NULL, expires_at TEXT NOT NULL)` と、`user_id` の索引
   - 既存の所有者の行（`login = 'owner'`）はパスワードが NULL のまま。管理者が CLI でパスワードとログイン ID を設定するまでログインできない
2. `Db` の操作：パスワードの設定・照合（失敗の回数と待ち時間を含む）、セッションの作成・引き当て（期限切れは無効として扱い、見つけたら消す）・削除、フィードのトークンの作成・引き当て
3. CLI `nucrawler user`
   - `user add <login> <表示名>`：利用者を作り、初期パスワードを作って 1 回だけ表示する
   - `user reset-password <login>`：新しいパスワードを作って表示し、その人のセッションを消す
   - `user rename <login> <新しい login>`：所有者の `owner` をメールアドレスに変えるときなどに使う
   - `user list`：login・表示名・管理者か・パスワードが設定済みか
   - 利用者の削除は作らない（必要になったら足す）。止めたいときは `reset-password` で本人に知らせないパスワードにする
4. Web
   - `/login`（GET：画面、POST：照合してセッションを作る）、`/logout`（POST）、`/settings/password`（POST）、`/settings/feed-token`（POST）
   - `viewer()` をやめ、セッションから利用者を引く extractor（例えば `Viewer { user, is_admin }`）に置き換える。プロファイルのハッシュは、使うハンドラで引く
   - 管理者だけの操作は、extractor の `is_admin` を見て 403 を返す
   - 画面のヘッダーにログイン中の表示名とログアウトを出す。設定画面に、パスワードの変更と、フィードの URL を出す
5. README の「認証は無いので…」を、認証の説明と「HTTP で待ち受けるので社内 LAN 内だけで使う」に書き換え、`user` の CLI を足す

## やらないこと

- HTTPS（証明書を用意できないため。Context を参照）
- 自分で登録する機能、メールでのリセット、二要素認証
- Entra ID などの OIDC
- 利用者ごとの採点。所有者以外にはプロファイルも採点も無いので、所有者以外の一覧には点数が付かない。
  プロファイルと記事のトピックからアルゴリズムで点数を出すことを、別の計画で扱う
- 和訳の依頼の制限。誰が依頼しても所有者の LLM の枠を使う。人数が少ないうちは制限しない
- JSON API のトークンでのアクセス。今は画面の JavaScript がブラウザの Cookie で使うだけなので、ほかから使う必要が出たら足す
- MCP と CLI の `search` などは、稼働ホストの利用者が使うものなので、今までどおり所有者として動かす

## テスト

- パスワードはハッシュで保存され、正しいパスワードでだけ照合に通る。パスワードが NULL の利用者はログインできない
- 失敗が続くと待ち時間の間は正しいパスワードでも通らず、成功すると失敗の回数が戻る
- セッション：期限切れのトークンでは利用者が引けない。ログアウトやパスワードのリセットで消える
- 未ログインの GET はログイン画面に回り、ログイン後に元のパスへ戻る。`//evil.example` のような戻り先は `/` に置き換える
- 未ログインの POST と `/api/...` は 401
- 2 人の利用者が同じ記事に付けた星・既読・ブックマークが、互いの画面に出ない
- フィード：トークンの利用者の既読で絞られる。トークンが無い・違うと 401。作り直すと古いトークンは 401
- 管理者でない利用者の訳語集の編集と指摘の処理は 403、管理者は通る
- 既存の Web のテストは、テスト用の利用者でログインした状態で通す（`test_support` にログイン済みの Cookie を付ける手段を足す）
