# プロファイルと記事のトピックから計算で採点する

## Context

計画 009 で、社内 LAN の複数の人が Web UI を使えるようにした。星・既読・ブックマークは利用者ごとに持っているが、
推薦の点数（採点）は所有者の分しか作られない。

- 採点は LLM が行う（`pipeline::score`）。利用者のプロファイル（関心分野と重み、推薦しない話題）を system prompt に入れ、
  要約済みの記事を数件ずつ渡して 0〜100 点と理由、当たった関心分野（`matched`）と推薦しない話題（`excluded`）を返させる
- LLM は所有者のサブスクリプションで動くので、利用者の数だけ採点を回すと、呼び出しが人数に比例して増える。
  所有者の 5 時間枠と週の枠を、ほかの人の採点で使い切りかねない
- 今は、所有者以外の利用者にはプロファイルも採点も無い。計画 009 の #140 で、プロファイルが無い利用者の一覧は
  「最低点なし・新しい順」にしたので、何も出ないことは無くなった。ただし関心に合わせた推薦はされない
- プロファイルを登録する手段は CLI の `nucrawler profile import`（所有者の分）しか無い

そこで、LLM を呼ばず、プロファイルと記事の要約に付いたトピックから計算で採点する。
計算の方法が LLM の採点にどこまで迫れるかは、所有者の評価（★1〜5）で `nucrawler eval` を使って測ってから、ほかの人に広げる。

### 使える材料

- **記事のトピック**：要約（digest）には、語彙（`topics`。分野・炉型・地域・組織の 4 つの軸で、初期は 55 語。要約の LLM が足した語が加わる）から選んだトピックが
  付いている（`artifact_topics`）。要約は記事ごとに LLM で 1 回作り、全員で共有するので、採点のために LLM を呼び足す必要が無い。
  統合した語の別名（`topic_aliases`）もある
- **要約の文**：見出しの和訳（`title_ja`）・要約（`summary_ja`）・要点（`points_ja`）。発電所名などの固有名は語彙に入れず、
  全文検索で探す方針（`0007_topics.sql` の注記、README の `topics` の項）なので、固有名の関心はこの文との照合で拾う
- **推薦点の補正**（`recommend.rs`、計画 004）：評価から、トピック・ソース・当たった関心分野（`score_matches` の interest）・
  推薦しない話題（exclude）ごとの重みを学び、採点の logit に足す。採点の出どころ（LLM か計算か）には依存しない
- **評価**（`eval`）：採点のキー（プロファイル・バックエンド・モデル・プロンプトの版）ごとに、評価との一致率（評価の違う記事の組のうち、
  評価の高いほうが高い点の割合。0.5 が当て推量）と、補正後の推薦点の一致率を出す

### 今のプロファイルと語彙はつながっていない

プロファイルの関心分野（`[[interest]] topic`）と推薦しない話題（`exclude`）は自由記述で、語彙とつながっていない。
LLM は自由記述でも読めるので困らなかったが、計算では当たりを判定できない。例のプロファイル（`examples/profile.toml`）でも、
「規制・審査」「燃料」「高経年化」「安全解析」「廃止措置」「政策・市場」は語彙の語と同じだが、「新設・SMR」は語彙では
「新設・建設」と「SMR」の 2 語、「バックエンド」は語彙に無い（「燃料サイクル・再処理」「使用済燃料・貯蔵」「放射性廃棄物」に当たる）。
`note`（採点の際に LLM へ渡す補足）の「ATF」「BWRX-300」「PRA」のような固有の語も、計算では使われない。

### 採点を選ぶ SQL が 4 か所ある

利用者の記事の採点を 1 件選ぶ SQL が、一覧（`Db::list_articles`）・和訳の先回り（`Db::pending_translate`）・
推薦点の補正の学習（`Db::recommend_examples`）・作り直し（`redo --min-score`）の 4 か所にあり、どれも
「利用者とプロファイルのハッシュが同じ採点のうち、プロンプトの版が新しく、点数の高いもの」を選ぶ
（`ORDER BY s.prompt_version DESC, s.score DESC`）。バックエンドとモデルは区別しない（モデル間では最高点を使う）。
計算の採点を同じ `scores` に入れると、所有者では LLM の採点と混ざって、版の大小や点数の大小で片方が選ばれてしまう。

## 方針

### 計算の採点は `scores` に入れる

計算の採点も `scores` の行として持ち、`backend = 'algorithm'`・`model = 'topics'`・`prompt_version = ALGORITHM_VERSION`
（計算の方法を変えたら上げる）とする。当たった関心分野と推薦しない話題は、LLM と同じく `score_matches` に入れる。

- `eval`・推薦点の補正・一覧・確認枠・和訳の先回りが、採点の出どころによらずそのまま使える
- プロファイルのハッシュごとに持つので、プロファイルを変えれば採点し直しになる（LLM の採点と同じ）
- 都度計算して持たない形（SQL の中で計算する）は取らない。`eval` と補正の学習が採点の行を前提にしていて、
  両方を計算の形に合わせて作り直すことになるため。計算は軽いので、持つ手間は小さい

### 利用者ごとに、使う採点（採点器）を決める

- 採点器は `llm`（LLM の採点）か `algorithm`（計算の採点）。所有者以外は `algorithm` だけ（LLM の枠を使わせない）。
  所有者は設定 `[recommend] owner_scorer`（既定 `llm`）で選ぶ。`eval` で比べてから切り替えられるように
- 採点を 1 件選ぶ 4 か所の SQL は、採点器で行を絞ってから今の規則で選ぶ。絞り方は 1 つの SQL の断片
  （`recommend_score_sql` と同じく関数で返す）にまとめ、4 か所がそれを使う（1 か所ずつ書くと、どこかで混ざる）
  - `llm`：`s.backend <> 'algorithm'`（今の規則。モデル間では最高点）
  - `algorithm`：`s.backend = 'algorithm'`
- 採点器は利用者から決まる値として、`ListQuery`・`SearchQuery`・`TranslateQuery` などに渡す

### 計算の採点は、所有者も含めてプロファイルのある全員に作る

所有者の分も作るのは、`eval` で LLM の採点と並べて測るため。所有者の一覧には、採点器を切り替えるまで出ない。

### プロファイルを語彙につなぐ

関心分野に、語彙の語（`topics`）と、要約の文で探す語（`keywords`）を持たせる。どちらも任意で、今のプロファイルはそのまま読める。

```toml
[[interest]]
topic = "新設・SMR"
weight = 0.4
note = "革新軽水炉、BWRX-300、NuScale など軽水炉型"
topics = ["新設・建設", "SMR"]
keywords = ["BWRX-300", "NuScale"]
```

- `topics` が無ければ、`topic`（関心分野の名前）が語彙の語か別名なら、その語を使う（「規制・審査」などはこれで当たる）
- `topics` の語は語彙の語か別名でなければならない。無い語は `profile import` で誤りにする（打ち間違いを採点の外れにしないため）
- `keywords` は、見出しの和訳・要約・要点と原題に、その語が含まれるかで当てる（大文字小文字を問わない）。
  全文検索の索引（trigram）は 3 文字未満の語を引けず、「ATF」「PRA」のような略語が落ちるので、採点のときに文字列で探す
- `exclude` の語は、語彙の語か別名なら、そのトピックが付いた記事に当てる。そうでなければ、`keywords` と同じく文字列で探す
- 語彙の語にも別名にもならず、`topics` も `keywords` も無い関心分野は、計算の採点では当たらない。
  `profile import` で、そういう関心分野を名前を挙げて知らせる（LLM の採点では使えるので、誤りにはしない）
- プロファイルのハッシュは `topics` と `keywords` も含めて計算する（変えれば採点し直し）
- `keywords` と、語彙の語でない `exclude` は文字列で探すので、空の文字列はすべての文に含まれ、全記事に当たる。
  `profile::validate` で、`topics`・`keywords` の空の値・空白だけの値・制御文字・重複を、`topic` や `exclude` と同じく誤りにする

### 計算の方法

記事ごとに、当たった関心分野の重みを noisy-OR でまとめる。関心分野 i の重みを w_i（0〜1）とし、

```text
当たった関心分野の集合 M、当たった推薦しない話題の集合 X
X が空でなければ 0 点
そうでなければ 点数 = round(100 × c × (1 − Π_{i∈M} (1 − w_i)))
```

- 当たりが増えるほど点が上がり、上限を超えない。重み 1 の分野に 1 つ当たれば 100c 点
- c（0〜1）は最高点の係数で、最初は 0.9 とする。一覧の既定の最低点（`web.min_score`、既定 50）に対して、
  重み 0.6 の分野 1 つ（54 点）から出て、重み 0.4 の分野 1 つ（36 点）では出ない
- 係数と式は計算の版（`ALGORITHM_VERSION`）に含め、変えたら版を上げる
- 理由（`reason`）には当たった関心分野と推薦しない話題を書く（例「当たった関心：規制・審査、燃料」）
- 採点する記事は LLM の採点と同じ（利用者が閲覧できる最新の要約があり、軽水炉に関係する記事。`Db::pending_score`）。
  要約の無い記事（本文が取れず要約できない）は採点しない
- 文で探す材料は、見出しの和訳・要約・要点・原題。今の採点の入力（`ScoreInput`）は見出しの和訳・要約・トピックだけなので、
  要点（`points_ja`）と原題を足す
- 軽水炉と関係があるか（`lwr_relevant`）は、今までどおり一覧の条件で別に見る（採点には入れない）

係数を数値の当て推量で詰めることはしない。所有者の評価で `eval` を回して、LLM の採点と一致率を比べてから決める。
補正（計画 004）がトピックごとの重みを評価から学ぶので、式が粗くても、評価が溜まれば個人ごとに合っていく。

### 採点のタイミング

- crawl に、LLM を使わない別のステージ（例 `match`）を `score` の後に置き、プロファイルのある利用者ごとに、
  `pipeline.backlog_days` の範囲の要約済みでまだ計算の採点が無い記事を採点する。LLM の枠・予約・失敗の記録（`stage_errors`）は使わない
  - `score` ステージの中に入れない。crawl は、LLM が使えない実行では LLM を使うステージを丸ごと飛ばす（`run.rs` の `llm_blocked`）ので、
    中に入れると LLM の停止で計算の採点まで止まる。別のステージなら、`Stage::llm_task` が無く、飛ばされない
- Web でプロファイルを保存したら、その場でその利用者の範囲の記事を採点する（次の crawl を待たずに一覧に効かせる）。
  記事の数は多くて数千件で、1 件は文字列の照合だけなので、要求の中で終わる

### 語彙が変わったら採点し直す

計算の採点は、プロファイル・計算の版・要約（`artifact_id`）のほかに、語彙にも依存する（語彙の語・別名・要約に付いたトピック）。
前の 3 つは採点のキーに入っているので、変われば別の採点になるが、語彙は入っていない。トピックの整理（`tidy` ステージの
`Db::merge_topics`）や `topics import`（`Db::replace_topics`）は、要約に付いたトピックと別名を書き換えるので、
同じキーのまま当たりが変わり、古い採点が残る。

- 語彙を変える処理ごとに採点を消す形にはしない。今後語彙を変える処理を足したときに、消し忘れるため
- DB のトリガーで消す。`topics`・`topic_aliases` の追加・更新・削除と、`artifact_topics` の更新・削除のたびに、
  計算の採点（`backend = 'algorithm'`。`score_matches` は外部キーで一緒に消える）を消す。消えた分は次の `match` ステージで作り直す
  - 要約に新しいトピックが付くこと（`artifact_topics` の追加）は、新しい要約（新しい `artifact_id`）のことで、既存の採点に効かないので対象にしない
  - 要約の LLM が語彙に新しい語を足すこと（`topics` の追加）も、既存の要約のトピックとプロファイルのつなぎ込み（取り込みの時点で確かめた語）を
    変えないが、トリガーを簡単に保つため対象に含める（週に数語で、作り直しは軽い）
- 語彙の変更はトピックの整理が週 1 回で、作り直しは文字列の照合だけなので、全員の分を消しても重くない

### Web でプロファイルを編集する

所有者以外は CLI を使えないので、設定画面からプロファイルを作り、直せるようにする。

- 語彙の語を軸（分野・炉型・地域・組織）ごとに並べ、語ごとに重み（なし・低 0.4・中 0.7・高 1.0）を選ぶ。選んだ語が関心分野になる
- 推薦しない話題は、語彙の語を選ぶか、語を行ごとに書く
- 固有名などの語（`keywords`）は、「語 = 重み」の形で行ごとに書く（語ごとに 1 つの関心分野になる）
- `note` は LLM の採点にしか効かないので、この画面には出さない。所有者が CLI で書いた `note` や、語彙の語でない関心分野
  （「バックエンド」など）は、画面で保存しても消さない（画面が扱わない項目はそのまま残す）
- 保存すると、`profile import` と同じ検証を通し、上の「採点のタイミング」のとおり採点する

## 変更

計画 009 と同じく、PR を分けて順に入れる。2 の後で `eval` の結果を見て、3 以降に進むかを決める。

1. プロファイルの `topics`・`keywords` と語彙へのつなぎ込み
   - `Interest` に `topics`・`keywords` を足す（`serde(default)`）。ハッシュに含める
   - `profile import` で、語彙に無い `topics` を誤りにし、計算では当たらない関心分野を知らせる
   - `examples/profile.toml` に、つなぎ込みの例を足す
2. 計算の採点と `eval` での比較
   - `src/algorithm.rs`（I/O を持たない）：プロファイル・記事のトピック・要約の文から、点数と当たりを返す
   - `ScoreInput` に要点と原題を足す
   - crawl に LLM を使わない `match` ステージを足し、プロファイルのある全員の分を作る（`backend = 'algorithm'`）
   - 語彙の変更で計算の採点を消すトリガー（マイグレーション）
   - `eval` の「今のキー」に、LLM の今の版に加えて計算の今の版も出す（今は LLM の版だけを「今」としている）
   - この段階では、一覧などが使う採点は変えない（4 か所の SQL は、`s.backend <> 'algorithm'` で今までどおり LLM の採点だけを見る）
3. 採点器の選択
   - 4 か所の SQL の絞り方を 1 つの断片にまとめ、利用者の採点器を渡す
   - 所有者以外は `algorithm`、所有者は `[recommend] owner_scorer`
4. Web でのプロファイルの編集と、保存時の採点

## やらないこと

- 所有者以外の LLM の採点（LLM の枠を使わせない）
- 記事の埋め込み（ベクトル）による類似度。外部のモデルか依存が要る。トピックと語の照合で足りないと `eval` で分かってから考える
- `profile suggest`（LLM がプロファイルの更新案を作る）を所有者以外に開くこと
- 計算の採点で、記事ごとの重要度（同じ分野の中で大きな話か）を見分けること。LLM が `note` を読んでしていたことで、
  計算では落ちる。補正が評価から学ぶ分と、`eval` で測った差を見て、必要なら要約の段階で記事の重要度を出させることを別に考える

## 見込みと判断の基準

- 本番の評価は 2026-09-27 時点で 10 件程度と少なく、一致率の誤差は大きい。数十件溜まってから比べる
- 計算の採点の一致率が LLM の採点と同じ程度なら、ほかの人に広げる（3・4 へ進む）。大きく下回るなら、
  どの評価の記事で外れたかを見て、プロファイルのつなぎ込み（`topics`・`keywords`）の不足か、式の問題かを分けてから直す

## テスト

- プロファイル：`topics`・`keywords` のある TOML とない TOML を読める。語彙に無い `topics` は誤り。別名は語彙の語として通る。
  `keywords`・`topics` の空の値・空白だけの値・制御文字・重複は誤り。
  計算では当たらない関心分野を名前つきで返す。`topics`・`keywords` を変えるとハッシュが変わる
- 計算：トピックで当たる、関心分野の名前が語彙の語なら当たる、`keywords` が文字列で当たる（大文字小文字を問わない、3 文字未満の語も）、
  推薦しない話題が当たれば 0 点、重みの noisy-OR と係数の境界（重み 1 の分野 1 つで 90 点、当たり無しで 0 点）、当たりが `score_matches` に入る
- ステージ：プロファイルのある全員の分を作り、作ったものは作り直さない、プロファイルを変えると作り直す、LLM を呼ばない。
  LLM が使えない実行（`llm_blocked`）でも走る
- 語彙：トピックの統合・語彙の取り込みで計算の採点が消えて作り直され、統合した語で当たる。新しい要約にトピックが付いても、ほかの記事の採点は消えない
- 入力：要点と原題にだけある語（例 原題の「NuScale」）が `keywords` で当たる
- `eval`：LLM と計算の今のキーが並ぶ
- 採点器：所有者で両方の採点があるとき、`llm` なら LLM の点、`algorithm` なら計算の点が、一覧・和訳の先回り・補正の学習・作り直しの
  4 か所で使われ、混ざらない。所有者以外は計算の点
- Web の編集：語の重みと推薦しない話題とキーワードを保存でき、画面が扱わない項目（`note`・語彙の語でない関心分野）が残る。
  保存するとその場で採点され、一覧に点数が付く。条件に反する入力は保存しない
