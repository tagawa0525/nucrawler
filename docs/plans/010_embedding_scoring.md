# 記事と好みの embedding の近さで採点する

## Context

計画 009 で、社内 LAN の複数の人が Web UI を使えるようにした。星・既読・ブックマークは利用者ごとに持っているが、
推薦の点数（採点）は所有者の分しか作られない。

- 採点は LLM が行う（`pipeline::score`）。利用者のプロファイル（関心分野と重み・補足の `note`、推薦しない話題）を
  system prompt に入れ、要約済みの記事を数件ずつ渡して 0〜100 点を返させる
- LLM は所有者のサブスクリプションで動くので、利用者の数だけ採点を回すと、呼び出しが人数に比例して増える
- 今は、所有者以外にはプロファイルも採点も無い。計画 009 の #140 で、プロファイルが無い利用者の一覧は
  「最低点なし・新しい順」にしたので、何も出ないことは無いが、関心に合わせた推薦はされない
- プロファイルを登録する手段は CLI の `nucrawler profile import`（所有者の分）しか無い

そこで、LLM で採点せず、**記事と利用者の好みを embedding（文章を意味のベクトルに変えたもの）にし、その近さで点数を付ける**。
推薦の分類でいう内容ベースの推薦（content-based filtering）で、今の「評価から学ぶ補正」（計画 004、`recommend.rs`。
learning to rank の一種）と組み合わせたハイブリッドにする。

### 採らなかった方式：プロファイルの語と記事のトピックの照合

この計画の最初の版（PR #145 の途中まで）は、プロファイルの関心分野を語彙の語（`topics`）と語（`keywords`）につなぎ、
要約に付いたトピックとの一致で、手で決めた重みを合成して点数にする方式だった。レビューと検討で、次の弱点が分かったのでやめた。

- 語彙に縛られる。語彙に無い言い回し・略語・新しく加わった語（要約の LLM が足す）では当たらず、プロファイルと語彙の対応を
  人が保ち続ける必要がある
- 手で決めた重みでは「見たくない」の強さや、多くの話題に少しずつ触れる記事（週報など）の扱いを表しにくい
- 点数を保存したので、語彙・プロファイル・係数の変更で古くなった点数を見つけて作り直す仕組み（語彙の世代、トリガー、
  計算と語彙の変更の競合）が要り、複雑になった

embedding なら、意味の近さで測るので語彙に依存せず、日本語と英語、「ATF」と「事故耐性燃料」のような言い換えも近くなる。
記事の embedding は要約から 1 回だけ作り、好みとの近さはその場で計算するので、点数を作り直す仕組みも要らない。

### 使う embedding のモデル（2026-10-01 の調査）

embedding はモデルが違うと互換性がない（同じ空間に無い）が、r995（個人の環境）と社内の環境は DB が別なので、
それぞれの中でモデルが揃っていればよい。

| 環境                                 | モデル                                                                                                                                               | 理由                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| r995（Ryzen 9 9950X・92 GB、非商用） | ローカルの `cl-nagoya/ruri-v3-310m`（Apache-2.0、768 次元）。比較の候補に `sbintuitions/sarashina-embedding-v2-1b`（非商用のライセンス、1,792 次元） | r995 は非商用なので、非商用のモデルも使える。JMTEB（日本語の embedding の比較）の平均・検索は sarashina が 76.38 / 76.48 で最上位、ruri が 75.85 / 76.03 で差は 0.5 ほど。ruri は r995 の CPU で約 3 件/秒（800 トークンの実測。実際の要約は 150〜400 トークンなので数倍速い）、sarashina は 1B パラメータでその 1/3 程度。どちらにするかは `eval` で決める |
| 社内（非力な VM）                    | Azure OpenAI の `text-embedding-3-large`                                                                                                             | VM では重いモデルを動かせない。会社の Azure で使える。JMTEB は 73.86 / 71.95。`text-embedding-3-small` は検索が 61.79 と低いので使わない                                                                                                                                                                                                                    |

- どちらも OpenAI 互換の embeddings API（`POST /v1/embeddings`、`{"model", "input", "dimensions"}` を送り `data[].embedding` を受ける）で呼べる。
  Azure の v1 API は URL が `https://<resource>.openai.azure.com/openai/v1/embeddings`、`model` がデプロイ名、認証が `api-key` ヘッダーになるだけ
- 費用：3-large は 1M トークン $0.13 前後で、1 日 300 件でも月 1 ドル、過去 3 万件の投入でも数ドル
- r995 のローカルの動かし方は、OpenAI 互換の embeddings API を出すローカルのサーバー（Hugging Face の text-embeddings-inference を Podman で動かすなど）
  を置き、HTTP で呼ぶ。nucrawler は API しか見ないので、サーバーの選び方はモデルが動くかで決める（変更の 1. の最初に確かめる）
- ruri はクエリと文書で接頭辞（「検索クエリ: 」「検索文書: 」）を付けて使う。サーバーは付けないので、クライアントが設定に従って付ける
- 社内の Azure OpenAI の利用申請と、VM から API へ通信できるかは、利用者が社内で確かめている（2026-10-01 時点で未確定）

## 方針

### embedding の呼び出しは 1 つのクライアントにする

- 設定 `[embedding]`：`url`、`model`（Azure ではデプロイ名）、`auth`（`bearer` か `api-key`。鍵は環境変数から読み、設定ファイルに書かない）、
  `dimensions`（任意）、`query_prefix`・`document_prefix`（任意）、1 回に送る件数、1 回の呼び出しのタイムアウト（`timeout_secs`、既定 30 秒。
  サーバーが応答しないまま止まると、crawl の `embed` ステージも Web のプロファイルの保存も止まるため）
- **保存は冪等にする**。同じ要約・同じプロファイルを同じ空間で作れば同じベクトルになるので、すでに行があれば何もしない（`ON CONFLICT DO NOTHING`）。
  重なった処理（予約の期限が切れた後の 2 つ目の `embed`、プロファイルの保存と `embed` ステージ）が同じものを作っても、後から保存する側は
  何も変えず、誤りにもならない。保存の直前に予約の持ち主を確かめる仕組みや、プロファイル用の予約は置かない（重複して呼ぶ費用は、
  記事は予約でほとんど防げ、プロファイルは多くて 100 件の短い文で小さい）
- 設定が無ければ embedding を使わない（今までどおり LLM の採点だけ）
- 保存するベクトルには、**ベクトルの空間を表す ID** を付け、同じ ID のベクトルどうしだけを比べる（空間が違えば互換性が無いため）
  - 設定（URL・モデル・次元・接頭辞）から作った名前だけでは足りない。Azure のデプロイ名やローカルのモデル名が同じまま、中身のモデルの版が
    替わることがあり、名前が同じでも空間が違うベクトルが混ざる
  - そこで**中身で見分ける**。決まった数件の試験文（指紋）を embedding にしたベクトルを、空間の ID と一緒に保存しておく。`embed` ステージ・
    プロファイルの保存のたびに指紋を作り直して比べ、コサイン類似度が十分 1 に近くなければ（例 0.999 未満）別の空間とみなし、新しい ID にする
  - 指紋は、試験文を**クエリとして**（好みのベクトルと同じ経路。`query_prefix` を付ける）と**文書として**（記事のベクトルと同じ経路。
    `document_prefix` を付ける）の両方で作り、次元の数も含めてすべて一致したときだけ同じ空間とみなす。片方の経路だけで作ると、
    片方の接頭辞だけを変えたときに気づかず、古い記事のベクトルと新しい好みのベクトル（または逆）が同じ空間として比べられてしまう
  - **入力の組み立て方の版**（`EMBEDDING_INPUT_VERSION`。記事の見出し・要約・要点のつなぎ方と、好みの名前・`note` のつなぎ方を変えたら上げる）も、
    空間を見分ける値に含める。指紋はモデルと接頭辞の変化しか見分けられず、組み立て方を変えても同じ空間のまま新旧のベクトルが混ざるため。
    版が変われば新しい `building` の空間になり、全件を作り直す（LLM の採点のプロンプトの版と同じ考え方）
  - **呼び出しのたびに確かめる**。指紋の確認と本体の呼び出しを別々にすると、全期間を作り直している途中でサーバーの中身が替わったとき、
    確認の後の呼び出しが別のモデルで作られても同じ空間に保存されてしまう。そこで記事や好みを送る呼び出しには、同じ経路の指紋の試験文も一緒に入れ、
    返ってきた指紋が空間の指紋と一致したときだけ、その呼び出しの結果を保存する。一致しなければ保存せず、空間が替わったものとして扱う
  - 新しい空間になったら、全記事と全員の好みのベクトルを作り直す（1 件 1 回の呼び出しで、費用も時間も小さい）
- **空間ごとにすべてを区切る**。空間の表 `embedding_spaces (id, name, fingerprint, state, created_at)` を置き、記事のベクトル・好みのベクトル・
  失敗の記録のキーに空間の ID を使う。名前（設定から作る）ではなく ID で区切るので、名前が同じまま中身が替わっても、
  新旧のベクトルや失敗の記録がぶつからない（古い空間で再試行の上限に達した記事も、新しい空間では最初から試す）
- **空間の切り替えの手順**。空間の状態は `active`（点数に使う。同時に 1 つ）・`building`（作っている。同時に 1 つ）・`retired`（使わない）
  - 「同時に 1 つ」は DB で守る。`active` と `building` それぞれに部分一意索引（`WHERE state = 'active'` など）を置き、指紋の確認・
    古い `building` の退役・新しい `building` の作成を 1 つの書き込みのトランザクション（`BEGIN IMMEDIATE`）で行う。crawl の `embed` と
    Web のプロファイルの保存は別の接続から同時に指紋を確かめうるので、読んでから書く間にほかが割り込まないようにする
  - 指紋が今の `active` の空間と違えば、`building` の空間を作り（すでに同じ指紋の `building` があればそれを使う）、そちらにベクトルを作っていく
  - 点数は、切り替えるまで `active` の空間で付ける（同じ空間の中で揃っているので比べられる）。`active` が無い初回は、`building` が切り替わるまで点数が付かない
  - **完了の条件**：`embed` ステージが対象にする**すべての要約**（全期間）と、プロファイルのある**全員の今のプロファイル**の好みについて、
    `building` の空間にベクトルができたか、`building` の空間で再試行の上限に達したこと。`active` の空間にあるものを基準にしない
    （初回は `active` が無いので何も作らないうちに完了とみなしてしまい、古い空間で失敗していたものも対象から漏れるため）。
    上限に達したものは、切り替えた後は点数が付かない（その件数を `status` に出す）。好みのベクトルが上限に達した利用者は、点数が付かないので
    最低点も掛からない（下記）
  - **切り替え**：完了の条件を、切り替えるのと同じトランザクションの中で判定し（判定と切り替えの間に要約やプロファイルが増えても漏らさないため）、
    満たしていれば `active` を `retired` に、`building` を `active` にする。点数を求める側は
    要求の初めに `active` の ID を 1 度だけ読むので、1 つの一覧の中で空間が混ざらない
  - `retired` の空間のベクトルは、切り替えの後に消す（失敗の記録も）。点数を求める側は、`active` の ID の読み出しからベクトルの読み出しまでを
    1 つの読み取りのトランザクションで行う（WAL の読み取りは始めた時点の内容を見る）ので、途中で古い空間が消されても、読んでいる内容は変わらない
  - 作っている途中で指紋がまた変われば、その `building` を `retired` にして、新しい `building` を作り直す
- ベクトルは L2 正規化して保存する（`dimensions` で切り詰めたときも正規化し直す）。近さは内積（= コサイン類似度）
- 応答を確かめてから保存する：返ったベクトルの数が送った数と同じ、どれも同じ次元で 0 でない、値がすべて有限。そうでなければ失敗として扱い、保存しない

### 記事の embedding

- 要約（`digest`）ごとに、見出しの和訳・要約・要点をつないだ文を文書として embedding にする。要約は日本語なので、日本語専用の ruri でもよい
- 原文や全文訳ではなく、**要約にそろえる**
  - 全文訳があるのは、依頼された記事と点数の高い記事だけ。「全文訳があれば全文訳」にすると、すでに選ばれた記事だけ材料が変わり、偏る
  - 長い文章は多くの話題を含んでベクトルがぼやけ、短い要約と比べると近さの出方が違う。材料が混ざると記事どうしを公平に比べられない
  - 訳が付いた時点でベクトルが替わり、同じ記事の順位が動く
  - 原文は英語と日本語が混ざり、PDF の全文のようにモデルの上限（8,192 トークン）を超えるものや、ページの定型文を含むものがある
  - 弱点は、要約で省かれた細部（特定の炉型名など）を拾えないことと、要約の出来に左右されること。細部を拾いたければ、
    材料を置き換えるのではなく、全文を区切った各部分との近さのうち大きいものを補いとして足すことを、`eval` で比べてから考える
- 重なって走る crawl が同じ要約を二重に呼ばないよう、ほかの LLM のステージと同じく作業の予約（`work_claims`、`Db::claim_selected`）を使い、
  対象を選ぶのと予約を 1 つのトランザクションで行う。予約は保存を終えるまで持つ
- 新しいステージ `embed` を要約の直後に置く。LLM のステージではない（`Stage::llm_task` が無い）ので、LLM が使えない実行でも飛ばされない
- 期間は区切らない（過去の評価した記事も `eval` で比べるため）。初回は全期間の要約を作り、以後は新しい要約だけ
- 失敗は `article_embedding_errors (artifact_id, space_id, attempts, next_retry_at, last_error)` に記録し、今のステージと同じ規則で間を空けて再試行する。
  今の `stage_errors` は使わない。そのキーは記事の ID までで要約の版（`artifact_id`）を持たないので、同じ記事の古い要約で上限に達すると、
  作り直した新しい要約まで止まってしまう（好みのベクトルの失敗の記録と同じく、対象の単位に合わせて別に持つ）
- 保存は `article_embeddings (artifact_id, space_id, vector BLOB)`、主キーは `(artifact_id, space_id)`。要約を作り直せば新しい `artifact_id` になり、
  自然に作り直される
- 閲覧の制限：要約の閲覧資格（会員限定の本文から作った要約）はそのまま `artifacts` 側で判定する。ベクトルは要約に付くので、読めない要約のベクトルは使わない

### 好みのベクトル

- プロファイルの関心分野ごとに、名前と `note` をつないだ文をクエリとして embedding にする（関心分野ごとのベクトル）。推薦しない話題も 1 つずつ
- プロファイルを保存・取り込みしたときに作る。作れなかったとき（サービスが止まっているなど）は、プロファイルは保存し、次の `embed` ステージで作る
- 保存は `profile_embeddings (user_id, profile_hash, space_id, kind, position, vector)`（kind は interest か exclude、position はプロファイルでの順）
- 好みのベクトルと失敗の記録は、**今のプロファイルにだけ**つながるよう DB で守る
  - `profiles` は利用者ごとに今のものを 1 行だけ持つ（`user_id` が主キー）ので、`(user_id, hash)` も一意にできる。その一意索引を置き、
    好みのベクトルと失敗の記録から `(user_id, profile_hash)` への外部キー（削除時は一緒に消す）を張る
  - ハッシュが変わる更新では、更新の前のトリガーで古いハッシュの好みのベクトルと失敗の記録を消す（外部キーの更新時の動作に「消す」が無いため）
  - これで、プロファイル A のベクトルを作っている間に B を保存しても、後から届いた A の結果や失敗は外部キーの違反で書けない（呼び出し側は
    プロファイルが替わったものとして捨てる）。古いものが残り続けることも、後で A に戻したときに古い失敗の記録が復活することも無い
  - A → B → A と戻り、最初の A のときの結果が後から届いた場合は書ける（ハッシュ A の行があるため）。これは正しい：ハッシュはプロファイルの中身から
    作るので、同じハッシュなら同じ文章から作ったベクトルになる（別のモデルのものが混ざらないことは、呼び出しごとの指紋の確認で守る）
- 1 つのプロファイルの好みのベクトルは、**全部そろうか、無いか**にする。一部だけのベクトルでは点数の意味が変わる（欠けた関心分野に近い記事が下がる）ため
  - 呼び出しは設定の「1 回に送る件数」（とサーバーの上限）で分け、結果はいったん手元に持つ。全部の呼び出しで指紋が空間と一致し、件数がそろったときだけ、
    1 つのトランザクションでまとめて保存する。どれかが失敗すれば何も保存せず、失敗として記録する
- 失敗の記録は、記事の `stage_errors`（記事の ID でしか対象を表せない）とは別に、`profile_embedding_errors (user_id, profile_hash, space_id,
  attempts, next_retry_at, last_error)` に持つ。再試行の間隔と上限は記事と同じ規則にする。プロファイルを変えればハッシュが変わるので、
  新しいプロファイルは最初から試す

### 点数の出し方

最初の式は次のとおりとし、係数と組み合わせ方は `eval` で比べて決める（下記「判断の手順」）。

- 記事と関心分野 i の類似度 s_i、推薦しない話題 j の類似度 t_j
- 関心の強さ：**重み付きの最大** `a = max_i (w_i × max(s_i, 0))`（足し合わせない。多くの話題に少しずつ触れる記事で上がりすぎないように）
- 見たくなさ：`b = max_j max(t_j, 0)`。推薦しない話題が 0 件なら `b = 0`（減点なし）。関心分野が 0 件なら `a = 0`
- 類似度は、0 未満を 0 に切り詰めてから使う（`s_i`・`t_j` とも）。コサイン類似度は負にもなり、そのままでは、推薦しない話題との類似度が負のときに
  加点になり、関心の類似度が負のときは重みの小さい分野ほど積が大きくなる（重みと除外が逆に効く）
- 生の値：`a − λ × b`（λ は設定 `[recommend] exclude_weight`、既定 1。有限で 0 以上でなければ設定の誤りにする。負なら減点が加点に変わり、
  NaN や無限大なら点数と並びが壊れるため）
- 点数（0〜100）：生の値を、**直近の記事の中での順位（百分位）**にする。基準の分布は、一覧の期間（`web.list_days`）の記事の生の値（N 件）。
  モデルごとに類似度の分布が違う（0.3〜0.8 に集まるモデルもある）ので、そのままの値では一覧の最低点（既定 50）の意味がモデルで変わる。
  百分位なら、50 は「直近の記事の上位半分」とどのモデルでも同じ意味になる
  - **母集団**は、利用者が閲覧できる最新の要約のうち、`active` の空間に記事のベクトルがあり、生の値を計算できるものだけ（N はその件数）。
    ベクトルが無い要約（作るのに失敗した、まだ作っていない）と閲覧できない要約は、母集団に入れず、その記事は**点数なし**（未採点と同じ扱い）
  - 生の値が 0 以下（どの関心分野とも近くない、または減点が上回る）なら 0 点
  - そうでなければ `round(100 × (基準の中で生の値が v より小さい件数 + 0.5 × v と等しい件数) / N)`（同点は中間の順位。四捨五入）
  - 基準が 0 件（期間に要約が無い）なら、生の値が正の記事は 50 点
  - 類似度を 0 で切り詰めるので 0 の同点は多く出るが、0 以下はすべて 0 点にするので、同点の扱いで表示の件数が大きく変わることは無い
- 評価が溜まったら、評価した記事のベクトルも好みに使う（例：高く評価した記事との類似度の最大を関心に加える）。どう使うかは `eval` で比べてから足す

点数は保存しない。一覧・和訳の先回り・補正の学習・`eval` のたびに、記事のベクトルと好みのベクトルから計算する。

- 計算の量：最大の設定では、期間の記事 3,000 件 × 関心分野と推薦しない話題 100 × 3,072 次元で、約 9 億回の積和になる。要求のたびに全部を
  計算すると遅く、非力な VM では特に効くので、次のようにする
  - 生の値（`a − λb`）を、利用者・プロファイルのハッシュ・空間の ID ごとに、**要約（`artifact_id`）を単位に**メモリに持ち（今の補正のモデルの持ち方と同じ）、
    （大きさは 1 要約あたり十数バイトで、要約 3 万件でも 1 人あたり数百 KB。利用者の数だけ持つが、プロファイルやハッシュが替わった古いものは捨てる）
    まだ計算していない要約の分だけ計算する。記事の単位にしないのは、要約を作り直すと記事の最新の要約が替わり、古い要約の値を使い続けてしまうため。
    新しい要約は 1 日数百件なので、要求ごとの計算は小さい
  - 一覧の SQL には、行ごとに Rust の関数を呼ばせず、Rust でまとめて求めた生の値と基準の分布を 1 つの引数（今の補正の重みと同じく JSON）で渡す
  - 空間の次元は `dimensions` で減らせる（3-large は 1,024 次元にしても精度の落ちが小さいとされる。`eval` で確かめる）
  - 変更の 2. で、最大の設定（関心分野 50・推薦しない話題 50・期間の記事の最大数）での一覧・補正の学習・`eval` の時間を測り、
    一覧の応答が 1 秒以内に収まることを確かめる。収まらなければ、次元を減らすか、生の値を DB に持つことを考える
- 補正（`recommend.rs`）の特徴は、今は LLM の採点の `score_matches`（当たった関心分野と推薦しない話題）から取っている。embedding では次のとおり決め、
  点数と一緒に返して、補正の特徴と詳細の理由に使う
  - Interest：重み付きの最大を取った関心分野（`a > 0` のとき）
  - Exclude：最も近い推薦しない話題のうち、減点が関心を上回ったもの（`λb ≥ a` かつ `b > 0` のとき）。どの記事もどれかの話題には少しは近いので、
    近さだけで付けると全記事に付いてしまう
  - Topic・Source は今までどおり（要約のトピックと記事のソース）

### 利用者ごとに、使う採点（採点器）を決める

- 採点器は `llm`（LLM の採点）か `embedding`。所有者以外は `embedding` だけ（LLM の枠を使わせない）。所有者は設定 `[recommend] owner_scorer`（既定 `llm`）
- 採点を 1 件選ぶ 4 か所の SQL（一覧の `Db::list_articles`、和訳の先回りの `Db::pending_translate`、補正の学習の `Db::recommend_examples`、
  作り直しの `redo --min-score`）は、今はどれも `ORDER BY s.prompt_version DESC, s.score DESC` で LLM の採点を選んでいる。
  「利用者の土台の点数」を返す 1 つの SQL の断片にまとめ、4 か所がそれを使う
  - `embedding`：embedding の点数
  - `llm`：LLM の採点を優先し、無い記事は embedding の点数で補う。LLM の採点はプロファイルのハッシュごとなので、プロファイルを変えると次の crawl まで無くなり、
    `backlog_days` より古い記事や LLM の枠が尽きたときにも無い。その穴を埋める
- 補正（`recommend.rs`）は、土台の点数の出どころによらずそのまま上に重ねる
- 所有者が `embedding` に切り替えた後も、LLM の採点（`score` ステージ）を続けるかは設定で選ぶ（`[recommend] keep_llm_scoring`、既定は続ける）。
  `eval` で比べ続けるには LLM の採点が要るが、比べ終えて要らなくなれば止めて LLM の枠を空けられる

### 点数が付きえないときは、最低点を掛けない

一覧は、プロファイルがあれば既定の最低点を掛ける（計画 009 の #140。プロファイルの有無を「点数に意味があるか」の目安にしている）。
この目安をやめ、**利用者の採点器で点数が付くときだけ**最低点を掛ける。

- 条件は、**一覧の期間に、土台の点数が付いた記事が 1 件以上あること**
  - これまで「出どころ（好みのベクトル、LLM の採点）が使えるか」で判定を重ねてきたが、そのたびに漏れが見つかった
    （記事のベクトルが 1 件も無い、LLM の採点が古いハッシュのものしか無い、など）。出どころの状態から「点数が付きうるか」を推し量らず、
    実際に点数が付いた記事があるかで決める。前の条件はすべてこの条件に含まれる
  - 例：`llm` の利用者がプロファイルを変えた直後は、新しいハッシュの LLM の採点も好みのベクトルもまだ無いので、点数の付いた記事が無く、
    最低点を掛けない（新しい順で全件が出る）。どちらかができて点数の付いた記事が現れれば、最低点が掛かる
  - 計算の順序は次のとおり固定する（最低点を決めるには点数が要り、一覧の SQL には最低点が要るので、順序を決めないと循環する）
    1. 一覧の期間の記事について、土台の点数（embedding の点数、`llm` なら LLM の採点との組み合わせ）を Rust で求める（生の値のキャッシュを使う）
    2. 点数の付いた記事の数から、最低点を掛けるかを決める（`default_min`）
    3. 1 の点数と 2 の最低点を引数にして、一覧の SQL を流す
- 判定は `default_min`（既定の最低点を 1 か所で決める関数）に、プロファイルのハッシュの有無の代わりに渡す
- MCP の検索（`mcp.rs`）も同じ判定を通す。今の MCP は `default_min` を通さず、隠すときはいつも設定の `web.min_score` を使うので、
  点数の付いた記事が無い利用者では、Web の一覧には新着が出るのに MCP の既定の検索は全件を隠す
- `profile import` は、重みが正の関心分野が無ければ誤りにする（早めに気づけるように）

### プロファイルの条件

- 関心分野は 50 件まで、推薦しない話題は 50 件まで、名前は 50 文字・`note` は 500 文字まで（好みのベクトルを作る呼び出しの量を抑える）。
  `profile::validate` に置き、CLI の取り込みと Web の保存の両方に効かせる

### Web でプロファイルを編集する

所有者以外は CLI を使えないので、設定画面からプロファイルを作り、直せるようにする。

- 関心分野を行ごとに入れる：名前（例「事故耐性燃料」）、補足（任意。例「ATF、Cr コーティング被覆管」）、重み（なし・低 0.4・中 0.7・高 1.0 から選ぶ）
- 推薦しない話題を行ごとに入れる
- 語彙から選ぶ形にはしない（embedding は語彙に依存しない）
- 保存すると `profile::validate` を通し、その場で好みのベクトルを作る。すべて「なし」ならプロファイルを消す
- 所有者が CLI で書いたプロファイルも、同じ画面で読み書きできる（形式は同じ：名前・`note`・重み・推薦しない話題）

## やらないこと

- 所有者以外の LLM の採点（LLM の枠を使わせない）
- 語彙の語やキーワードとの照合による採点（上記「採らなかった方式」）
- 協調フィルタリング（利用者と評価が少ないうちは効かない）
- ベクトルの索引（近傍探索の索引）。記事は数万件で、全件の内積でも十分速い
- 記事の英語の原題を embedding に入れること（要約は日本語で、日本語専用のモデルも使うため）。英語の原題が要るとわかったら、多言語のモデルで比べる

## 判断の手順（`eval`）

本番の評価は 2026-09-27 時点で 10 件程度と少なく、一致率の誤差は大きい。数十件溜まってから比べる。所有者の評価（★1〜5）を正解に、
同じ記事の集合で次を比べる。

1. LLM の採点と embedding の点数の一致率（今の `eval` の一致率と、補正後の一致率）
2. 関心分野ごとのベクトル・`note` を入れるか・評価した記事のベクトルを使うか
3. 重み付きの最大と、ほかのまとめ方（平均、上位 k の平均）
4. `dimensions` を減らしたとき（3-large の 3072 → 1024）の落ち方
5. 接頭辞の有無
6. r995 のモデル（ruri-v3-310m と sarashina-embedding-v2-1b）

embedding の一致率が LLM と同じ程度なら、ほかの人に広げる（3・4 へ進む）。大きく下回るなら、外れた記事を見て、好みの作り方か式かを分けてから直す。

## テスト

- クライアント：OpenAI 互換の応答を読める、Azure の `api-key` の形で送る、`dimensions` と接頭辞を付ける、正規化する、失敗を返す
  （テストでは手元の HTTP サーバーで応答を返す）
- `embed` ステージ：要約ごとに 1 回作り、作ったものは作り直さない、設定のモデルを変えると作り直す、LLM が使えない実行でも走る、
  失敗は要約の版と空間ごとに残って再試行される（同じ記事の古い要約で上限に達しても、新しい要約は試される）、全期間の要約が対象
- 好みのベクトル：プロファイルの保存・取り込みで作られ、作れなくてもプロファイルは保存され、次の `embed` で作られる
- 点数：重み付きの最大（重い分野に近い記事が上）、推薦しない話題に近い記事が下がる、百分位（基準の期間の中央が 50 点）、
  類似度が負のとき（推薦しない話題との類似度が負でも加点にならない、関心の類似度が負でも重みの小さい分野が選ばれない）、
  空間の ID が違うベクトルは使わない、閲覧できない要約のベクトルは使わない。生の値は計算していない記事の分だけ計算される
- 好みのベクトル：関心分野と推薦しない話題が全部そろったときだけ保存される。失敗は利用者・プロファイル・空間ごとに記録され、間を空けて再試行される。
  上限に達したプロファイルは空間の完了の条件を妨げず、その利用者は点数が付かず最低点も掛からない
- 補正の特徴：Interest は最大を取った分野、Exclude は減点が関心を上回ったときだけ付く
- 空間の削除：古い空間を消しても、消す前に始めた読み取りの点数は変わらない
- 空間の完了の条件：初回（`active` が無い）は、全要約と全員の好みのベクトルを作るか上限に達するまで切り替わらない。
  古い空間で失敗していた要約も、新しい空間で作られる。判定と切り替えの間に増えた要約があれば切り替わらない
- 指紋：`query_prefix` だけ・`document_prefix` だけ・`dimensions` だけを変えても、新しい空間になる
- 空間：同じ設定のまま指紋が変わる（サーバーの中身のモデルを替える）と `building` の空間ができ、全記事と好みが作り直される。
  作り直している間は `active` の空間で点数が付き、完了の条件（再試行の上限に達したものを含む）を満たすと 1 つのトランザクションで切り替わる。
  古い空間で再試行の上限に達した記事も、新しい空間では試される。作っている途中で指紋がまた変わると、作り直しがやり直しになる
- 百分位：同点は中間の順位、生の値が 0 以下は 0 点、基準が 0 件のとき、推薦しない話題が 0 件のとき（減点なし）
- 生の値のキャッシュ：同じ記事の要約を作り直すと、新しい要約の値が計算される
- `eval`：LLM と embedding のキーが並ぶ。`--profile` の候補の embedding の点数が、本番のプロファイルを変えずに並ぶ。
  embedding のキーには「反応の後に採点した」注意が出ない
- MCP：点数の出どころが無い利用者では、既定の検索で記事が隠れない
- 呼び出しごとの指紋：本体の呼び出しで返った指紋が空間と違えば、その結果は保存されない
- 空間の一意性：2 つの接続から同時に指紋の違いを見つけても、`building` は 1 つだけできる
- プロファイルの差し替え：古いハッシュの好みのベクトルと失敗の記録が消える。A のベクトルを作っている間に B を保存すると、
  後から届いた A の結果も失敗も書けない（段階を分けて呼んで確かめる）
- 入力の版：`EMBEDDING_INPUT_VERSION` を上げると新しい空間になり、全件が作り直される
- 応答の検証：件数が合わない・次元がそろわない・0 ベクトル・NaN を含む応答は保存されず、失敗として記録される
- LLM の採点を続けるか：`keep_llm_scoring = false` で所有者が `embedding` なら、`score` ステージが LLM を呼ばない
- 冪等な保存：同じ要約・同じプロファイルのベクトルを 2 つの処理が同時に作っても、両方とも誤りにならず、行は 1 つだけ残る
- タイムアウト：応答しないサーバーへの呼び出しは `timeout_secs` で失敗になり、失敗として記録される
- 予約：2 つの crawl が同時に `embed` を走らせても、同じ要約は 1 回しか呼ばれない
- 百分位の母集団：ベクトルの無い要約・閲覧できない要約は N に入らず、その記事は点数なし
- 最低点：記事のベクトルが期間に 1 件も無い（好みのベクトルはある）と、点数の付いた記事が無いので最低点が掛からない
- λ の設定：0 と有限の正の値は通り、負の値・NaN・無限大は設定の誤り
- 好みのベクトルの分割：「1 回に送る件数」より多い関心分野でも、分けて呼んで全部そろえば保存され、どれかが失敗すれば何も保存されない
- 採点器：所有者で `llm` なら LLM の点、無い記事は embedding の点、`embedding` なら embedding の点が、4 か所で使われる。所有者以外は embedding の点
- 最低点：一覧の期間に点数の付いた記事が無いとき（好みのベクトルが無い・重みが正の関心分野が無い・`llm` の利用者がプロファイルを変えた直後で
  新しいハッシュの LLM の採点も好みのベクトルも無い）、一覧に最低点が掛からない。点数の付いた記事が現れれば掛かる
- プロファイルの条件：件数と長さの境界、重みが正の関心分野が無い TOML は誤り
- Web の編集：関心分野と推薦しない話題を保存でき、その場で好みのベクトルが作られ、一覧に点数が付く。すべて「なし」でプロファイルが消える
