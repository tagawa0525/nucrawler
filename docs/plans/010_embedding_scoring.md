# 記事と好みの embedding の近さで採点する

## Context

計画 009 で、社内 LAN の複数の人が Web UI を使えるようにした。星・既読・ブックマークは利用者ごとに持っているが、
推薦の点数（採点）は所有者の分しか作られない。

- 採点は LLM が行う（`pipeline::score`）。利用者のプロファイル（関心分野と重み・補足の `note`、推薦しない話題）を
  system prompt に入れ、要約済みの記事を数件ずつ渡して 0〜100 点を返させる
- LLM は所有者のサブスクリプションで動くので、利用者の数だけ採点を回すと、呼び出しが人数に比例して増える
- 今は、所有者以外にはプロファイルも採点も無い。計画 009 の #140 で、プロファイルが無い利用者の一覧は
  「最低点なし・新しい順」にしたので、何も出ないことは無いが、関心に合わせた推薦はされない
- プロファイルを登録する手段は CLI の `nucrawler profile import`（所有者の分）しか無い

そこで、LLM で採点せず、**記事と利用者の好みを embedding（文章を意味のベクトルに変えたもの）にし、その近さで点数を付ける**。
推薦の分類でいう内容ベースの推薦（content-based filtering）で、今の「評価から学ぶ補正」（計画 004、`recommend.rs`）と組み合わせる。

規模の前提：r995 の DB は 2026-10-01 時点で利用者 1 人・要約約 1,600 件・評価 18 件。社内も数人。
要約は 1 日数百件増える。この規模に合わせ、無停止の移行や細かい競合の防止より、単純さと早期の失敗を選ぶ。

### 採らなかった方式

1. **プロファイルの語と記事のトピックの照合**（PR #145 の最初の版）。語彙に無い言い回しで当たらず、手で決めた重みでは
   「見たくない」の強さを表しにくい。また、点数が語彙（キーに入らない、後から変わる入力）に左右されたので、保存した点数を
   語彙の変更に合わせて作り直す仕組み（語彙の世代・トリガー・計算との競合の防止）が要り、複雑になった
2. **embedding の点数を保存せず、要求のたびに計算する**（PR #145 の後半の版）。1 の教訓から保存を避けたが、
   百分位の基準の計算、メモリのキャッシュ、最低点の判定との循環、点数を選ぶ SQL・MCP・`eval` の個別の対応が要り、
   さらにモデルの入れ替えを止めずに行う仕組み（空間の状態遷移・完了の条件）と、好みのベクトルをプロファイルの行に結び付ける仕組み
   （外部キー・トリガー・ABA の対応）を重ねて、レビューのたびに仕組みが増えた。
   embedding の点数は、入力（要約・プロファイル・モデル・式）をすべて版やハッシュとしてキーに入れられるので、1 の作り直しの問題は起きない。
   そこで既存の `scores` 表に LLM の採点と並べて保存する（下記）

### 使う embedding のモデル（2026-10-01 の調査）

embedding はモデルが違うと互換性がない（同じ空間に無い）が、r995（個人の環境）と社内の環境は DB が別なので、
それぞれの中でモデルが揃っていればよい。

| 環境                                 | モデル                                                                                                                       | 理由                                                                                                                                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| r995（Ryzen 9 9950X・92 GB、非商用） | ローカルの `cl-nagoya/ruri-v3-310m`（Apache-2.0、768 次元）。比較の候補に `sbintuitions/sarashina-embedding-v2-1b`（非商用） | JMTEB（日本語の embedding の比較）の平均・検索は sarashina が 76.38 / 76.48 で最上位、ruri が 75.85 / 76.03。ruri は r995 の CPU で約 3 件/秒（800 トークン）、sarashina はその 1/3 程度。どちらにするかは `eval` で決める |

- どちらも OpenAI 互換の embeddings API（`POST /v1/embeddings`、`{"model", "input", "dimensions"}` を送り `data[].embedding` を受ける）で呼べる。

  nucrawler は API しか見ない
- ruri はクエリと文書で接頭辞（「検索クエリ: 」「検索文書: 」）を付ける。サーバーは付けないので、クライアントが設定に従って付ける
- 社内の Azure OpenAI の利用申請と、VM から API へ通信できるかは、利用者が社内で確かめている（2026-10-01 時点で未確定）

## 方針

### embedding のクライアント

- 設定 `[embedding]`：`url`、`model`（Azure ではデプロイ名）、`auth`（`bearer` か `api-key`。鍵は環境変数から読む）、
  `dimensions`（任意）、`query_prefix`・`document_prefix`（任意）、1 回に送る件数（`batch_size`。下記の指紋の試験文を含めて数え、
  試験文の数より大きくなければ設定の誤り）、`timeout_secs`（既定 30 秒。0 は誤り）
- 設定が無ければ embedding を使わない（今までどおり LLM の採点だけ）
- 応答を確かめる：返ったベクトルの数が送った数と同じ、どれも同じ次元で 0 でない、値がすべて有限。そうでなければ失敗にする
- ベクトルは L2 正規化して保存する（`dimensions` で切り詰めたときも）。近さは内積（= コサイン類似度）

### モデルが替わったら止まる（空間は 1 つだけ）

DB が持つベクトルの空間は常に 1 つにし、モデルが替わったら**誤りで止めて、作り直しのコマンドを案内する**。
モデルの入れ替えはまれで、作り直しは r995 で数時間・Azure で数ドル。作り直しの間は embedding の点数が無くなるだけで、
一覧は「点数の付いた記事が無ければ最低点を掛けない」（下記）で新しい順に戻る。

- 表 `embedding_space`（1 行だけ）に、世代（`id INTEGER PRIMARY KEY AUTOINCREMENT`。消した後も同じ値を使い回さない）、設定から作った名前（URL・モデル・次元・接頭辞）、入力の組み立て方の版
  （`EMBEDDING_INPUT_VERSION`。記事と好みの文のつなぎ方を変えたら上げる）、**指紋**を持つ
- 指紋は、決まった試験文（2 件）を、クエリとして（`query_prefix` を付ける）と文書として（`document_prefix` を付ける）の両方で
  embedding にしたベクトル。名前が同じままデプロイの中身が替わることがあるので、中身で見分ける
- 記事や好みを送る呼び出しには、同じ経路の指紋の試験文（2 件）も一緒に入れ、残りの `batch_size − 2` 件に記事や好みを載せる。返った指紋が保存した指紋とコサイン類似度 0.999 以上で一致したときだけ、
  その呼び出しの結果を保存する
- 名前・版・指紋のどれかが違えば、`embed` ステージは誤りで止まり（そのステージの残りを打ち切り、ほかのステージは続ける）、
  `nucrawler embed rebuild` を案内する。プロファイルの保存（段階 4）では、プロファイルは保存し、好みのベクトルは作らない
- 1 行だけであることは DB で守る（`singleton INTEGER NOT NULL UNIQUE CHECK (singleton = 1)` の列を置く）
- 初回（行が無い）は、`embed` ステージの**始め**にだけ、指紋を作って行を入れる。行の有無の確認と挿入は 1 つの書き込みのトランザクション
  （`BEGIN IMMEDIATE`）で行う。2 つの `embed` が同時に始まっても、後の側は先の側が入れた行を読み、名前・版・指紋をふだんどおり比べてから進む。ステージは始めに世代を 1 度だけ読み、以後の保存はすべてその世代に対して行う。
  途中で行が無くなっても、作り直して続けることはしない（`rebuild` の前に始まった処理が古いモデルで空間を作り直し、`rebuild` を取り消してしまうため）
- `nucrawler embed rebuild` は、1 つのトランザクションで、すべてのベクトル・embedding の点数・`embed` の失敗の記録・`embedding_space` の行を消す。
  次の `embed` ステージが新しいモデルで初回として作り直す
- ベクトルと点数の保存は、ステージの始めに読んだ世代の行がまだあることを確かめるのと同じ書き込みのトランザクション（`BEGIN IMMEDIATE`）で行う。
  無ければ保存せず、そのステージを打ち切る。`rebuild` と重なった `embed` が、古いモデルのベクトルや、`rebuild` の前に読んだベクトルから
  計算した点数を、`rebuild` の後に保存しようとしても保存されない（新しい空間ができていても、世代が違う）

### ベクトルの保存

- 記事：`article_embeddings (artifact_id PRIMARY KEY, vector BLOB)`。要約（`digest`）ごとに、見出しの和訳・要約・要点をつないだ文を文書として作る。
  要約を作り直せば新しい `artifact_id` になり、自然に作り直される
- 好み：`text_embeddings (input_hash PRIMARY KEY, vector BLOB)`。プロファイルの関心分野ごとの「名前と `note` をつないだ文」と、
  推薦しない話題 1 つずつを、クエリとして作る。キーは**接頭辞を付けた入力の文のハッシュ**で、利用者やプロファイルには結び付けない
  - 同じ文なら誰がいつ作っても同じベクトルなので、プロファイルの差し替えと作成が重なっても、古い結果が届いても、誤りにならない
  - 使われなくなった行は、`embed` ステージの終わりに、今のどのプロファイルの文にも当たらないものを消す
- 保存は `INSERT ... ON CONFLICT DO NOTHING`（冪等）
- 閲覧の制限：ベクトルと点数は要約に付く。一覧はこれまでどおり、利用者が読める要約だけを選んでから点数を引く

### 記事の材料は要約にそろえる

- 全文訳があるのは、依頼された記事と点数の高い記事だけ。全文訳を使うと、すでに選ばれた記事だけ材料が変わり、偏る
- 長い文章は多くの話題を含んでベクトルがぼやけ、短い要約と比べると近さの出方が違う
- 原文は英語と日本語が混ざり、PDF の全文のようにモデルの上限を超えるものや、ページの定型文を含むものがある
- 弱点は、要約で省かれた細部を拾えないこと。拾いたくなれば、全文を区切った各部分との近さを補いとして足すことを `eval` で比べてから考える

### `embed` ステージ

要約（`digest`）の直後に新しいステージ `embed` を置く。LLM のステージではない（`Stage::llm_task` が無い）ので、LLM が使えない実行でも飛ばされない。
順に次を行う。

1. 記事のベクトル：ベクトルの無い要約を、全期間から選ぶ（過去の評価した記事も `eval` で比べるため）。ほかのステージと同じく
   作業の予約（`Db::claim_selected`）を使う。失敗は `stage_errors` に、採点と同じくステージ名に範囲を入れて記録する（`embed:<artifact_id>`。
   主キーが記事の ID までなので、要約の版を名前に含め、同じ記事の古い要約の失敗が新しい要約を止めないようにする）。再試行の規則は今のステージと同じ
2. 好みのベクトル：プロファイルのある全員について、ベクトルの無い文を作る。失敗は記録せず、次の実行でまた試す（多くて 100 件の短い文で、
   1 回の実行で 1 回呼ぶだけなので、間隔を空ける必要が無い）
3. 採点：プロファイルのある全員について、embedding の点数がまだ無い要約を採点する（下記）。計算はメモリで済むので（全期間でも数秒）、
   利用者ごとに、その回に採点した点数を 1 つのトランザクションでまとめて保存する。一覧などからは、ベクトルのある要約の点数は
   全部あるか、まだ無いかのどちらかに見え、一部だけ採点された状態で最低点が掛かることは無い

### 点数の式

最初の式は次のとおりとし、係数と組み合わせ方は `eval` で比べて決める（下記「判断の手順」）。

- 記事と関心分野 i の類似度 s_i、推薦しない話題 j の類似度 t_j。どちらも 0 未満は 0 に切り詰める
  （そのままでは、推薦しない話題との類似度が負のときに加点になり、関心の類似度が負のときに重みの小さい分野ほど積が大きくなる）
- 関心の強さ：**重み付きの最大** `a = max_i (w_i × s_i)`（足し合わせない。多くの話題に少しずつ触れる記事で上がりすぎないように）。関心分野が 0 件なら `a = 0`
- 見たくなさ：`b = max_j t_j`。推薦しない話題が 0 件なら `b = 0`
- 生の値：`a − λ × b`。λ は設定にせず、コードの定数にする（既定 1）
- 点数（0〜100）：生の値を、**採点した時点での、直近の記事の中での順位（百分位）**にする。
  モデルごとに類似度の分布が違う（0.3〜0.8 に集まるモデルもある）ので、そのままの値では一覧の最低点（既定 50）の意味がモデルで変わる
  - 基準は、その利用者について、一覧の期間（`web.list_days`）の最新の要約のうち、ベクトルがあるものを新しい順に最大 3,000 件
    （定数 `SCORE_REFERENCE_LIMIT`。期間の設定や記事の増え方で計算量が膨らまないように）取った生の値（N 件）。採点のたびに計算し直す
    （最大で 3,000 件 × 100 × 3,072 次元。計測は段階 2 で行う）
  - 生の値が 0 以下なら 0 点。そうでなければ `round(100 × (基準の中で v より小さい件数 + 0.5 × v と等しい件数) / N)`。基準が 0 件なら 50 点
  - 点数は採点した時点の基準で固まる。同じ記事でも、後の日に採点していれば違う点になりうるが、LLM の点数もその時点の判断で固まっているのと同じとみなす
- 式・λ・百分位の基準の取り方・入力の組み立て方を変えたら、版（`EMBEDDING_SCORE_VERSION`）を上げる。LLM のプロンプトの版と同じく、
  新しい版の点数が付けば古い版より優先される

### 点数を `scores` に保存する

既存の `scores` 表は `(user_id, artifact_id, profile_hash, backend, model, prompt_version)` をキーにしている。
embedding の点数を `backend = 'embedding'`、`model = embedding_space の名前`、`prompt_version = EMBEDDING_SCORE_VERSION` で保存する。

- 点数を決める入力はすべてキーに入る：要約（`artifact_id` は不変）、プロファイル（ハッシュ）、モデル（名前。中身の入れ替えは `rebuild` で全部消す）、
  式（版）。語彙のような、キーの外で変わる入力が無いので、作り直しの仕組みは要らない
- プロファイルを変えればハッシュが変わり、次の `embed` で全期間が採点し直される（3 万件 × 100 × 768 次元で数秒）。古いハッシュの点数は、
  LLM の採点と同じく使われなくなるだけ
- 補正の特徴（`score_matches`）も一緒に保存する
  - interest：重み付きの最大を取った関心分野（`a > 0` のとき）
  - exclude：最も近い推薦しない話題（`λb ≥ a` かつ `b > 0` のとき。近さだけで付けると全記事に付いてしまう）
- これで、一覧・和訳の先回り・補正の学習・`redo --min-score`・`eval` は、保存した点数をそのまま読める

### `eval` では保存せずに試す

本番は保存した点数を使い、式の候補を試すときだけ、その場で計算する。

- 保存した embedding の点数は、`eval` のキー（`backend`・`model`・`prompt_version`）として LLM の採点と自動で並ぶ
- 式は I/O を持たないモジュールにし、係数とまとめ方を引数で受ける。`eval` は、保存したベクトルから候補の式（λ、平均・上位 k の平均など）の点数を
  その場で計算し、別のキーとして並べる
  - 式どうしを比べるときは、今の式もその場で計算し直し、すべての候補と同じ時点・同じ基準で百分位にする。保存した点数は採点した時点の基準で
    固まっているので、そのまま候補と比べると、式の差に採点の時期の差が混ざる。保存した点数は本番の実績として別に並べる
- `eval --profile`（候補のプロファイルを今のものと並べる）でも、候補の好みのベクトルを作って（`text_embeddings` に入れてよい。キーが文のハッシュなので
  本番のプロファイルに影響しない）、その場で計算して並べる
- `eval` の「反応の後に採点した」注意（LLM のプロンプトの版 1 が直近の反応の見出しを含んでいたため）は、LLM のキーだけに出す

### 利用者ごとに、使う採点（採点器）を決める（段階 3）

- 採点器は `llm`（LLM の採点）か `embedding`。所有者以外は `embedding` だけ。所有者は設定 `[recommend] owner_scorer`（既定 `llm`）
- 点数を 1 件選ぶ SQL（一覧の `Db::list_articles`、和訳の先回りの `Db::pending_translate`、補正の学習の `Db::recommend_examples`、
  `redo --min-score`）は、今はどれも `ORDER BY s.prompt_version DESC, s.score DESC`。これを 1 つの SQL の断片にまとめ、採点器で並びを変える
  - `embedding`：`backend = 'embedding'` の点数だけ
  - `llm`：LLM の点数を優先し、無い記事は embedding の点数で補う（`ORDER BY (s.backend = 'embedding'), s.prompt_version DESC, s.score DESC`）。
    プロファイルの変更の直後や、`backlog_days` より古い記事、LLM の枠が尽きたときの穴を埋める
- 補正（`recommend.rs`）は、点数の出どころによらずそのまま上に重ねる
- 所有者が `embedding` に切り替えた後も LLM の採点を続けるかは、`[recommend] keep_llm_scoring`（既定は続ける）。`eval` で比べ終えたら止めて枠を空けられる

### 点数が付かないときは、最低点を掛けない（段階 3）

一覧は、プロファイルがあれば既定の最低点を掛ける（計画 009 の #140）。これを、**一覧の期間に、利用者の今のプロファイルのハッシュで、
利用者の採点器が選ぶ点数の付いた記事が 1 件以上あるとき**だけ掛けるようにする。

- 点数は保存してあるので、一覧の SQL より前に `EXISTS` の問い合わせ 1 つで決まる（計算の順序の循環は無い）
- embedding の点数は利用者ごとにまとめて保存する（上記「`embed` ステージ」の 3）ので、採点の途中の一部の点数で最低点が掛かることは無い
- 判定は `default_min` に、プロファイルのハッシュの有無の代わりに渡す
- MCP の検索（`src/mcp.rs`）も同じ判定を通す。今は `default_min` を通さず、いつも `web.min_score` で隠す
- 例：プロファイルを変えた直後は、新しいハッシュの点数がまだ無いので、最低点を掛けず新しい順に全件が出る。次の `embed` で点数が付けば掛かる

### プロファイルの条件（段階 2）

- 関心分野は 50 件まで、推薦しない話題は 50 件まで、名前は 50 文字・`note` は 500 文字まで（好みのベクトルを作る量を抑える）。
  `profile::validate` に置き、CLI の取り込みと Web の保存の両方に効かせる
- 重みが正の関心分野が無ければ誤りにする

### Web でプロファイルを編集する（段階 4）

## 判断の手順（`eval`）

本番の評価は 2026-10-01 時点で 18 件と少なく、一致率の誤差は大きい。数十件溜まってから比べる。所有者の評価（★1〜5）を正解に、
同じ記事の集合で次を比べる。

1. LLM の採点と embedding の点数の一致率（今の `eval` の一致率と、補正後の一致率）
2. `note` を入れるか、評価した記事のベクトルを好みに使うか（例：高く評価した記事との類似度の最大を関心に加える）
3. 重み付きの最大と、ほかのまとめ方（平均、上位 k の平均）、λ の値
4. `dimensions` を減らしたとき（3-large の 3072 → 1024）の落ち方
5. 接頭辞の有無
6. r995 のモデル（ruri-v3-310m と sarashina-embedding-v2-1b）

3 は保存したベクトルからその場で計算できる。4〜6 はモデルや設定を変えるので、`rebuild` をして作り直してから比べる。
embedding の一致率が LLM と同じ程度なら、ほかの人に広げる（3・4 へ進む）。大きく下回るなら、外れた記事を見て、好みの作り方か式かを分けてから直す。

## テスト

段階 1・2 の分を挙げる。3・4 のテストは、その段階の PR で決める。

- クライアント：OpenAI 互換の応答を読める、Azure の `api-key` の形で送る、`dimensions` と接頭辞を付ける、正規化する。
  件数が合わない・次元がそろわない・0 ベクトル・NaN を含む応答と、`timeout_secs` を超えた呼び出しは失敗になる（手元の HTTP サーバーで返す）。
  `batch_size` が試験文の数（2）以下なら設定の誤り、3 なら 1 件ずつ送って進む
- 空間：初回に `embedding_space` ができる。空の状態から 2 つの `embed` が同時に始まっても、行は 1 つだけできる。名前・入力の版・指紋（クエリだけ・文書だけの変化も）が違うと `embed` が誤りで止まり、何も保存しない。
  呼び出しの中の指紋が違えば、その結果は保存されない。`rebuild` の後の `embed` で全件が作り直される。`rebuild` の前に始まった `embed` は、`rebuild` の後にベクトルも点数も保存できず、空間の行も作り直さない（世代が使い回されない）
- 記事のベクトル：要約ごとに 1 回作り、作ったものは作り直さない。LLM が使えない実行でも走る。全期間の要約が対象。
  失敗は要約ごとに記録され再試行される（同じ記事の古い要約が上限に達しても、新しい要約は試される）。2 つの crawl が同時に走っても、同じ要約は 1 回しか呼ばれない
- 好みのベクトル：同じ文は 1 回だけ作られる。使われなくなった文の行は消える
- 点数の式：重い分野に近い記事が上、推薦しない話題に近い記事が下。類似度が負でも加点にならず、重みの小さい分野が選ばれない。推薦しない話題が 0 件なら減点なし
- 百分位：基準の中央が 50 点、同点は中間の順位、生の値が 0 以下は 0 点、基準が 0 件なら 50 点、ベクトルの無い要約は基準に入らない、
  基準は期間の新しい順に 3,000 件まで
- 保存：`backend = 'embedding'` の点数と `score_matches`（interest は最大を取った分野、exclude は減点が関心を上回ったときだけ）が保存される。
  プロファイルを変えると新しいハッシュで全期間が採点される。利用者の 1 回の採点の保存が途中で失敗すると、その回の点数は 1 件も残らない。好みのベクトルがそろっていない利用者は採点されない。
  版を上げると新しい版で採点される
- 段階 2 では、一覧・和訳の先回り・補正の学習・`redo --min-score` が embedding の点数を使わない
- プロファイルの条件：件数と長さの境界、重みが正の関心分野が無い TOML は誤り
- `eval`：LLM と embedding のキーが並び、候補の式と `--profile` の候補が、本番の点数とプロファイルを変えずに並ぶ。
  候補の式と今の式は同じ基準で計算し直され、保存した点数とは別に並ぶ。embedding のキーには「反応の後に採点した」注意が出ない
