# 記事と好みの embedding の近さで採点する

この計画は、何をなぜ決めたかを残す。競合や端のケースの扱いは、各段階の実装の PR でテストとともに決める。

## Context

計画 009 で、社内 LAN の複数の人が Web UI を使えるようにした。星・既読・ブックマークは利用者ごとに持っているが、
推薦の点数（採点）は所有者の分しか作られない。

- 採点は LLM が行う（`pipeline::score`）。プロファイル（関心分野と重み・補足の `note`、推薦しない話題）を system prompt に入れ、
  要約済みの記事を渡して 0〜100 点を返させる
- LLM は所有者のサブスクリプションで動くので、利用者の数だけ採点を回すと、所有者の枠を使い切りかねない
- 所有者以外には、プロファイルも採点も無い（計画 009 の #140 で、プロファイルが無い利用者の一覧は「最低点なし・新しい順」）
- プロファイルを登録する手段は CLI の `nucrawler profile import`（所有者の分）しか無い

そこで、LLM で採点せず、**記事と利用者の好みを embedding（文章を意味のベクトルに変えたもの）にし、その近さで点数を付ける**。
内容ベースの推薦で、今の「評価から学ぶ補正」（計画 004、`recommend.rs`）はそのまま上に重ねる。

規模の前提：r995 の DB は 2026-10-01 時点で利用者 1 人・要約約 1,600 件・評価 18 件。社内も数人。要約は 1 日数百件増える。
この規模に合わせ、無停止の移行や細かい最適化より、単純さと早期の失敗を選ぶ。

### 採らなかった方式

1. **プロファイルの語と記事のトピックの照合**（PR #145 の最初の版）。語彙に無い言い回しで当たらず、手で決めた重みでは
   「見たくない」の強さを表しにくい。また、点数がキーに入らない入力（語彙）に左右されたので、保存した点数を作り直す仕組みが複雑になった
2. **embedding の点数を保存せず、要求のたびに計算する**（PR #145 の後半の版）。1 の教訓から保存を避けたが、百分位の基準・キャッシュ・
   最低点の判定・モデルの無停止の入れ替え・プロファイルに結び付けたベクトルの整合と、仕組みが重なって収束しなかった。
   embedding の点数は入力（要約・プロファイル・モデル・式）をすべて版やハッシュとしてキーに入れられるので、1 の問題は起きない

### 使う embedding のモデル（2026-10-01 の調査）

r995（個人の環境）と社内の環境は DB が別なので、それぞれの中でモデルが揃っていればよい。

| 環境                     | モデル                                                                                                                 | 理由                                                                                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| r995（CPU のみ、非商用） | ローカルの `cl-nagoya/ruri-v3-310m`（Apache-2.0、768 次元）。候補に `sbintuitions/sarashina-embedding-v2-1b`（非商用） | JMTEB（日本語の embedding の比較）の平均・検索は sarashina が 76.38 / 76.48、ruri が 75.85 / 76.03。ruri は r995 の CPU で約 3 件/秒（800 トークン）。どちらにするかは `eval` で決める |
| 社内（非力な VM）        | Azure OpenAI の `text-embedding-3-large`                                                                               | VM で重いモデルを動かせない。会社の Azure で使える。JMTEB は 73.86 / 71.95。`text-embedding-3-small` は検索が 61.79 と低い                                                             |

- どちらも OpenAI 互換の embeddings API で呼べる（Azure の v1 API は `model` がデプロイ名、認証が `api-key` ヘッダー）。
  r995 では OpenAI 互換の API を出すローカルのサーバー（text-embeddings-inference を Podman で動かすなど）を置く
- 費用：3-large は 1M トークン $0.13 前後。1 日 300 件で月 1 ドル、過去 3 万件で数ドル
- ruri はクエリと文書で接頭辞（「検索クエリ: 」「検索文書: 」）を付ける。クライアントが設定に従って付ける
- 社内の Azure OpenAI の利用申請と VM からの通信は、利用者が社内で確かめている（2026-10-01 時点で未確定）

## 決めたこと

### 点数は既存の `scores` 表に保存する

`scores` は `(user_id, artifact_id, profile_hash, backend, model, prompt_version)` をキーにしている。embedding の点数を
`backend = 'embedding'`、`model` = 空間の名前、`prompt_version` = 式の版で保存し、補正の特徴も `score_matches` に入れる。

- 点数を決める入力のうち、変わりうるもの（要約・プロファイルのハッシュ・モデル・式）はキーに入るので、作り直しの仕組みは要らない。
  プロファイルや式を変えれば、新しいキーで採点し直す。百分位の基準（下記）だけはキーに入れず、採点した時点の値で固める
  （同じキーを計算し直すと違う点になりうるが、計算し直すのは `rebuild` で全部消した後だけなので、新旧が混ざらない）
- 一覧・和訳の先回り・補正の学習・`redo --min-score`・`eval` は、LLM の採点と同じく保存した点数を読む
- 採点は要約の直後の新しいステージ `embed` で行う。LLM のステージではないので、LLM が使えない実行でも走る。計算は内積だけで、
  プロファイルを変えた後の全期間の採点も数秒

### モデルが替わったら止まり、作り直す

DB が持つベクトルの空間は常に 1 つにする。

- 設定（URL・モデル・次元・接頭辞）と入力の組み立て方の版に加え、決まった試験文のベクトル（指紋。クエリと文書の両方）を保存する。
  名前が同じままデプロイの中身が替わることがあるので、中身で見分ける
- どれかが違えば `embed` は誤りで止まり、`nucrawler embed rebuild`（ベクトルと embedding の点数を全部消す）を案内する
- 作り直しの間は embedding の点数が無くなるだけで、一覧は新しい順に戻る（下記の最低点の規則）。モデルの入れ替えはまれで、
  作り直しは r995 で数時間・Azure で数ドルなので、止めずに入れ替える仕組みは作らない

### ベクトルの持ち方

- 記事：要約（`digest`）ごとに 1 つ。要約を作り直せば新しい要約のベクトルを作る
- 好み：プロファイルの関心分野ごとの「名前と `note` をつないだ文」と、推薦しない話題 1 つずつ。
  キーは**入力の文のハッシュ**にし、利用者やプロファイルには結び付けない。同じ文なら誰がいつ作っても同じベクトルなので、
  プロファイルの差し替えとベクトルの作成が重なっても整合の仕組みが要らない

### 記事の材料は要約にそろえる

- 全文訳があるのは、依頼された記事と点数の高い記事だけ。全文訳を使うと、すでに選ばれた記事だけ材料が変わり、偏る
- 長い文章は多くの話題を含んでベクトルがぼやけ、短い要約と比べると近さの出方が違う
- 原文は英語と日本語が混ざり、モデルの上限を超えるものや、ページの定型文を含むものがある
- 弱点は、要約で省かれた細部を拾えないこと。拾いたくなれば、全文を区切った各部分との近さを補いとして足すことを `eval` で比べる

### 閲覧の制限は LLM の採点と同じにする

会員限定の本文から作った要約は、読めない利用者の採点にも百分位の基準にも使わない（今の `Db::pending_score` と同じ条件）。
記事のベクトルは要約ごとに 1 つで、誰にも見せない。

### 点数の式

最初の式は次のとおりとし、係数とまとめ方は `eval` で比べて決める。

- 記事と関心分野 i の類似度 s_i、推薦しない話題 j の類似度 t_j。どちらも、その文と百分位の基準の要約との類似度の
  平均と標準偏差で標準化し、0 未満は 0 に切り詰める（負のままでは、推薦しない話題が加点になり、重みの小さい分野ほど積が大きくなる）
  - 標準化は、段階 2 の後の `eval`（2026-10-04、評価 43 件）で足した。ruri-v3 はどの文どうしも類似度が 0.73〜0.86 に集まり、
    「核融合」との類似度が関心分野との類似度（重み付き）と同じ程度になって、a − λb の符号が誤差で決まっていた
    （要約の約 4 分の 1、★4 の半分が 0 点）。標準化で今の式の一致率は 0.36 から 0.44（LLM と同じ程度）になった
- 関心の強さ：**重み付きの最大** `a = max_i (w_i × s_i)`（足し合わせない。多くの話題に少しずつ触れる記事で上がりすぎないように）
- 見たくなさ：`b = max_j t_j`。生の値は `a − λ × b`（λ はコードの定数、最初は 1）
- 点数（0〜100）：生の値を、**採点した時点での、その利用者の直近の記事の中での百分位**にする。モデルごとに類似度の分布が違うので、
  そのままでは一覧の最低点（既定 50）の意味がモデルで変わる。基準は一覧の期間の新しい要約（上限あり）。生の値が 0 以下なら 0 点
- 点数は採点した時点の基準で固まる。LLM の点数もその時点の判断で固まっているのと同じとみなす
- 補正の特徴：interest は重み付きの最大を取った関心分野、exclude は減点が関心を上回ったときの最も近い推薦しない話題

### `eval` では保存せずに試す

保存した embedding の点数は、`eval` のキーとして LLM の採点と自動で並ぶ。式の候補（λ、平均・上位 k の平均など）と
候補のプロファイル（`eval --profile`）は、保存したベクトルからその場で計算して並べ、本番の点数は変えない。
式どうしを比べるときは、今の式も同じ時点・同じ基準で計算し直す。

### 採点器と最低点（段階 3）

- 利用者ごとに採点器を決める：`llm` か `embedding`。所有者以外は `embedding` だけ。所有者は設定で選ぶ（既定 `llm`）。
  `llm` は LLM の点数を優先し、無い記事（プロファイルの変更の直後、`backlog_days` より古い記事、LLM の枠が尽きたとき）を embedding の点数で補う
- 点数を選ぶ 4 か所の SQL（`list_articles`・`pending_translate`・`recommend_examples`・`redo --min-score`）を 1 つの断片にまとめる
- 最低点は、**一覧の期間に、利用者の今のプロファイルで点数の付いた記事が 1 件以上あるとき**だけ掛ける（今の「プロファイルがあれば掛ける」をやめる）。
  点数が付かない間に一覧が空になるのを防ぐ。MCP の検索も同じ判定を通す
- 今の `llm_score`（`ListItem`・JSON・MCP・画面の「LLM {点数}」）は、出どころが embedding にもなるので、中立の名前と出どころ（`llm` か `embedding`）を
  加えて画面に出す。JSON（`/api/articles`）と MCP の `llm_score` は公開のフィールドなので、使う側が移るまで同じ値で残す

### Web でプロファイルを編集する（段階 4）

所有者以外は CLI を使えないので、設定画面からプロファイルを作り、直せるようにする。関心分野を行ごとに名前・補足・重み（なし・低・中・高）で入れ、
推薦しない話題も行ごとに入れる。詳細は段階 3 までの結果を見て別の計画にする。

## 変更

PR を分けて順に入れる。2 の後で `eval` の結果を見て、3 以降に進むかを決める。テストはそれぞれの PR で決める。

1. embedding のクライアントと記事のベクトル
   - 最初に、r995 で ruri と sarashina を OpenAI 互換の API で出せるローカルのサーバーを決める
   - `[embedding]` の設定と OpenAI 互換のクライアント（Azure の `api-key` にも対応。タイムアウトと応答の検証を持つ）
   - 空間と指紋、`nucrawler embed rebuild`
   - `embed` ステージの記事のベクトル（全期間。ほかのステージと同じ作業の予約と失敗の記録を使う）
   - r995 の home-manager の設定に、embedding のサーバーの unit を足す
2. 好みのベクトルと点数の保存、`eval` での比較
   - プロファイルの条件（関心分野・推薦しない話題は各 50 件、名前 50 文字・`note` 500 文字まで、重みが正の関心分野が 1 つは要る）
   - 好みのベクトル、点数の式、`scores`・`score_matches` への保存
   - 点数を選ぶ SQL は、この段階では embedding の点数を除き、一覧などの動きを変えない
   - 最大の設定で採点の時間を測る
   - `eval` の候補の式と候補のプロファイル。「反応の後に採点した」注意（LLM のプロンプトの版 1 のため）は LLM のキーだけに出す
3. 採点器の選択と最低点
4. Web でのプロファイルの編集（別の計画）

## やらないこと

- 所有者以外の LLM の採点
- モデルの入れ替えを止めずに行うこと
- 語彙の語やキーワードとの照合による採点
- 協調フィルタリング（利用者と評価が少ないうちは効かない）
- ベクトルの索引（記事は数万件で、全件の内積で十分速い）
- 記事の英語の原題を embedding に入れること（要約は日本語で、日本語専用のモデルも使うため）

## 判断の手順（`eval`）

本番の評価は 2026-10-01 時点で 18 件と少ない。数十件溜まってから、所有者の評価（★1〜5）を正解に、同じ記事の集合で次を比べる。

1. LLM の採点と embedding の点数の一致率（補正の前と後）
2. `note` を入れるか、評価した記事のベクトルを好みに使うか
3. 重み付きの最大と、ほかのまとめ方（平均、上位 k の平均）、λ の値
4. `dimensions` を減らしたとき（3-large の 3072 → 1024）の落ち方
5. 接頭辞の有無、r995 のモデル（ruri と sarashina）

3 は保存したベクトルからその場で計算できる。4・5 はモデルや設定を変えるので、`rebuild` をしてから比べる。
embedding の一致率が LLM と同じ程度なら、ほかの人に広げる（段階 3・4 へ進む）。大きく下回るなら、外れた記事を見て、好みの作り方か式かを分けてから直す。
