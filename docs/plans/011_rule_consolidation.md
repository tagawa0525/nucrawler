# 書き写した規則を 1 か所にまとめる

## 背景

2026-10-02 に、コード全体（本体は約 1.9 万行、ほかにテストが約 2.7 万行）からリファクタリングの候補を洗い出した。
冗長さの中心は行数ではなく、**同じ規則を何か所にも書き写し、直すときに一部を取り残す**ことだった。直前の 3 件
（eval の embedding 採点を本番と共通にする #152、閲覧できる最新の要約の SQL を断片にする #153、古い版のための
ロックをやめる #154）も同じ形で、eval の embedding 採点は本番に合わせる後追いの修正が 3 回入っていた。

取り残しはすでにバグになっている（A〜C）。残りは、骨組みの修正のたびに同じ変更を何ファイルにも並べて入れている
もの（D〜I）と、使われていないコードや実態と合わないコメント（J）。

## 方針

- 規則を 1 か所に置き、ほかはそれを呼ぶ。直すときに取り残せない形にする
- バグになっているものは TDD（失敗するテスト → 修正）で、それ以外は振る舞いを変えないリファクタリングで直す
- 抽象化は「すでに 3 か所以上ある」か「2 か所でも片方だけ直されて食い違った」ものに限る
- 1 項目を 1 PR にし、A から順に入れる。E は計画 010 の段階 3（点数を選ぶ SQL の統合）と触る行が隣り合うので、
  段階 3 より先に入れる

## A. MCP の検索が Web の一覧の既定を自前で組み立てている（バグ）

今は `mcp.rs` の `search` が、期間・最低点・隠す条件を独自に作る。

```rust
// 既定は Web UI の一覧と同じく隠す
hide_below: (!params.include_hidden).then(|| params.min_score.unwrap_or(web.min_score)),
```

Web の一覧は、プロファイルが無い利用者には最低点を掛けない（採点が無いので、掛けると何も出ない）。この規則
（`web/server/pages.rs` の `default_min`）は `pub(super)` で MCP から使えず、それを入れた変更（4ac731c）は MCP を
取り残した。そのため、プロファイルの無い利用者が MCP で既定のまま検索すると 0 件になる。最低点の範囲（0〜100）も
MCP だけ検査していない。

変更：

- 「利用者の既定の最低点」の規則を `web/server` の外（設定の側）に 1 か所だけ置き、Web と MCP の両方が使う
- `SearchQuery::hide_below: Option<u8>` は「隠すか」と「最低点（無ければ推薦点で絞らない）」を 1 つの値で表して
  いて、「隠すが最低点なし」を表せない。2 つに分ける
- MCP の最低点は Web と同じく 0〜100 を検査する
- MCP の検索は Web の検索と同じ条件（既読も出し、同じ報道をまとめない）で、一覧とは違う。ツールの説明と README
  の「Web UI の一覧と同じく」をそれに合わせる（振る舞いは変えない）

## B. LLM の応答の外枠の検証が 4 か所に書き写され、扱いが食い違っている（バグ）

採点・要約・見出しの和訳・同じ報道の判定の 4 つのプロンプトが、応答の外枠の検証（最上位がオブジェクト、`items`
以外のキーを拒む、`items` が配列、依頼していない id を捨てる、欠けた id を数える）をそれぞれ書いている。写すうちに、
整数の `id` が無い項目の扱いが分かれた。

- 採点と要約：`Malformed("an item has no integer id")` を返し、バッチ全体が失敗になる（バッチの全記事に失敗を記録）
- 見出しの和訳と同じ報道の判定：その項目だけを捨て、欠けた記事として扱う（その記事だけに失敗を記録）

変更：

- 外枠の検証と欠けの計算を `prompt` に 1 つ置き、4 つのプロンプトはそれを呼ぶ。項目ごとの検証は各プロンプトに残す
- `id` の無い項目は「その項目だけを捨てる」にそろえる。1 件の不正でほかの記事の結果まで捨てるのは損が大きく、
  捨てた記事は欠けとして失敗に記録されるので、次の実行で作り直される

## C. 行を崩す文字の判定が 3 通りある（バグ）

LLM が作る文字列から、端末の表示やプロンプトの行の構造を壊す文字を拒む判定が、3 通りに分かれている。

- 見出しの和訳：制御文字と、半角・全角以外の空白を拒む
- 要約が提案する語の名前：制御文字と、半角以外の空白を拒む（U+2028/U+2029 を拒む修正 9876184 はここにだけ入った）
- プロファイル（関心分野の名前・補足、推薦しない話題）と `profile suggest` の根拠：制御文字だけを拒む

プロファイルは採点の system prompt に 1 行ずつ埋め込まれるので、U+2028/U+2029 が通ると行の構造が壊れうる。

変更：

- 判定を `prompt` に 1 つ置き、すべての箇所から呼ぶ
- 名前（語彙の語、関心分野の名前、推薦しない話題）は半角の空白だけを許す。照合のキーなので、見た目の同じ別の語を
  作らない。文（補足、根拠、見出しの和訳）は全角の空白も許す
- 2026-10-02 時点の r995 のプロファイルに、新しく拒む文字は含まれていない（保存済みのプロファイルが条件を満たさ
  なくなると、embedding の採点は取り込み直すまで止まる）

## D. LLM ステージの作業ループの骨組みが 5 ステージに複製されている

要約・採点・和訳・見出しの和訳・同じ報道の判定の 5 ステージは、作業ループの骨組みを約 30 行ずつ書き写している
（周の始めに他の作業者に譲る → 止まったかを見る → 中断を見る → 呼び出しの枠を取る → もう一度止まったかを見る →
クォータの判定 → 呼び出し → 回数を数え予約を更新する → 結果を振り分け、LLM の失敗なら持っている記事に記録する
→ 止まるなら他の作業者にも知らせる → 結果を集計する）。`profile suggest` と語彙の整理も、1 回だけ呼ぶ形で同じ
手順を持つ。

骨組みの修正は毎回、同じ変更を 4〜7 ファイルに並べて入れている（9397602、96958c7、9bbb2c8、d73b552）。後から
写した同じ報道の判定では、すでにコメントの抜けがある。中断で終わった呼び出しを数えるかも、作業ループと 1 回だけの
呼び出しで違う。

変更：

- 周の始めの判定（譲る・止まったか・中断・枠・クォータ）と、呼び出しの結果の振り分けを `pipeline::llm_call` に
  置き、各ステージは「対象を選ぶ・プロンプトを作る・応答を解釈して保存する」だけを書く
- 各ステージの集計（`*Summary`）に共通の項目（失敗の数・呼び出しの数・止めた理由・中断）を 1 つの型にまとめ、
  集計の合わせ方（`merge`）の重複をなくす
- 中断で終わった呼び出しの数え方はそろえる（呼び出しは始まっているので数える）

## E. 「閲覧できる最新の要約」を選ぶ相関サブクエリが 7 か所以上ある

PR #153 で、閲覧できる要約のうち記事ごとの最新を選ぶ CTE（`read::latest_digests`）は 1 つにした。同じ規則を
相関サブクエリで書いた箇所が、一覧・評価の根拠・先回りの和訳・推薦の学習・`redo --min-score`・同じ報道の記事・
報告の一覧に残っている。

```sql
(SELECT r.id FROM artifacts AS r
 WHERE r.article_id = a.id AND r.kind = 'digest' AND {viewable}
 ORDER BY r.created_at DESC, r.id DESC LIMIT 1)
```

この上に、和文の見出しの規則（要約の見出し → 見出しの和訳）が 3 か所、点数が当たった語（関心分野・推薦しない
話題）の読み出しが 3 か所重なっている。先回りの和訳だけが「どれかの要約の最高点」を見ていたのを直した修正
（a672808）は、規則を各所で書いていたために起きた食い違いだった。

変更：最新の要約の id・和文の見出し・当たった語の 3 つを、`read::viewable` と同じく SQL の断片にする。CTE の
`latest_digests` は、まとめて選ぶ場面の実行計画を変えないよう残し、2 つが同じ規則であることを doc で示す。

## F. 「失敗で待っている記事と、ほかの実行が予約中の記事を除く」条件が 6 か所ある

要約・見出しの和訳・和訳・採点・同じ報道の判定の対象を選ぶクエリと `redo` が、同じ 2 つの `NOT EXISTS`（失敗の
記録で再試行待ちか断念済み、作業の予約が残っている）を書いている。予約の条件を足したとき（452c172）は全箇所を
同時に直す必要があり、その後に足したステージで写しが増えた。

変更：`viewable` と同じく、パラメータの名前を引数に取る断片にする。embedding のクエリは失敗の記録と予約で
ステージの式が違うので含めない。

## G. embedding の「試験文を付けて呼び、指紋を照合する」処理が 3 か所ある

要約のベクトル（まとめて呼ぶ・1 件ずつ送り直す）と好みの文のベクトルの 3 か所が、試験文を先頭に足して呼び、
中断と競わせ、試験文の結果で同じモデルかを確かめる処理を書いている。誤りの文言も 3 回書いている。

変更：試験文を付けて呼び、照合した結果だけを返す関数を 1 つ置く。入力のせいの失敗をどう扱うか（1 件ずつ送り
直すか）は呼び出し側に残す。

## H. claude と copilot の呼び出しの後半処理が同じ

2 つの CLI のバックエンドは、プロセスの起動の設定、タイムアウトまでに出た使用量を拾う処理、異常終了を中断と
区別する処理が同じで、使用量の型だけが違う。タイムアウトの前の使用量を残す修正（498c175）は、同じ 18 行を
両方に入れた。中断の判定（`interrupted`）は両方で使うのに claude 側にある。

変更：後半処理と `interrupted` を `llm::process` に移し、バックエンドは出力の解釈だけを渡す。

## I. Web の一覧の既定の規則がサーバーと HTML の 2 か所にある

評価やブックマークで絞り込むときは最低点を外して既読も出す、という規則を、一覧のハンドラ（`pages.rs` の
`list`）と、画面の URL を作る `ListView`（正規の URL へのリダイレクトにも使う）の両方が書いている。片方だけ
変えるとリダイレクトがループするか既定がずれる。4ac731c でも両方を直す必要があった。

変更：規則は `ListView` にだけ置き、ハンドラは `ListView` から既定を受け取る。

## J. 使われていないコードと、実態と合わないコメント

1 つの PR でまとめて片付ける。

- `rescore` コマンド：ヘルプに出るが実装が無く、実行すると `NotImplemented` で失敗する。コマンドと受け皿を消し、
  コマンドの振り分けを網羅的にする（足し忘れをコンパイラが見つける）
- テストからしか使われていない関数（`Quota::record_call`、`robots::Rules::disallow_all`、`Db::schema_version`）
- `pipeline::lock::try_lock` の関数ポインタの引数：共有と排他を使い分けるためのもので、#154 の後は排他しか渡さない
- `check.rs`（`sources check` 用で「DB には書かない」と説明している）に、crawl の取得処理（`fetch_source`）が
  置かれている。取得の側に移す
- crawl の振り分け（`pipeline::run`）で、ステージと LLM の工程の対応を分岐ごとに書き直している。対応表
  （`Stage::llm_task`）から 1 回だけ求める
- 実態と合わないコメントと README：#154 の後に残ったロックの説明（README の「ロックは `redo` と同じ」、
  `--wait-lock` の説明、`tests/crawl_lock.rs` の冒頭）、呼び出しの枠を「claude の数」とする説明（copilot も
  同じ枠を使う）、`llm` モジュールの「`llm.backend` で選ぶ」、MCP モジュールの冒頭、README の使い方に
  `embed rebuild` と `redo --max-llm-calls` が無いこと

## やらないこと

- `coalesce(a.published_at, a.fetched_at)`（約 30 か所）は断片にしない。1 行で意味が分かり、食い違った履歴も無い
- JSON API と MCP の記事の形（項目名や項目の有無が違う）は、意図した違いかを決めるのが先なので、ここでは扱わない
- 呼び出し後の使用率を、メモリと DB の 2 つの経路でクォータに反映している件は、メモリの経路を外して判定が変わら
  ないかを確かめてから別に決める
- 長い関数の分割（一覧のクエリの組み立て、`eval` の表示、報告の画面）は、この計画の項目を入れて規則が減った後に
  改めて見る
- ソースの種類（`kind`）と一覧の設定（`list`）を別の値で持つため、ありえない組み合わせを場合分けしている件は、
  設定の型の見直しになるので別に扱う
