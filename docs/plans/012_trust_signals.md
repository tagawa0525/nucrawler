# 処理の結果を信用できるかを確かめる

## 背景

2026-10-02、外部レビュー（ChatGPT に現行の main を読ませたコードレビュー）の追加提案を、コードと照合した。
レビューの主張は「機能は足りている。今後のリスクは、機能が増えた結果どこまで信用してよいシステムか分からなく
なること。機能追加より評価・観測・異常検知に寄せるべき」。

照合すると、提案のうち取得の「成功したように見える欠落」の検知（`Warning::SourceEmpty`・`SourceDropped`・
`SourceStale`）と、確認枠による閾値未満の見逃し率（`eval` の `render_explore`）はすでに入っていた。残りは次の 3 つで、
どれも「間違った結果や止まった処理が、警告もなく正常に見える」ことが共通の原因だった。

1. 同じ報道のグループが、LLM が「別の出来事」と判定した記事どうしをまとめてしまうことがある（A）
2. 再試行を諦めた記事が、ログ以外のどこにも出ない。`help` は `status` を「ステージごとの未処理件数などを表示」と
   説明しているが、実際はソースの取得状況しか出さない（B）
3. 「途中で止めても次の実行で再開できる」がステージごとのテストでしか確かめられておらず、ステージをまたいだ
   再開を確かめるテストが無い（C）

## 方針

- 1 項目を 1 PR にし、A → B → C の順に入れる。A は振る舞いが誤っているので TDD で直す
- 新しい指標や判定を足すより、すでに DB にある事実（LLM の判定、`stage_errors`）を使う

## A. 同じ報道のグループが、別の出来事という判定を無視してつながる

今は `Db::rebuild_stories` が、記事ごとの最新の判定から same の組だけを取り出し、`story::components` が素集合で
つなぐ。判定が割れた組を外す条件は、同じ組を相手が same 以外にしている場合だけ。

```sql
WHERE x.relation = 'same'
  AND NOT EXISTS (
    SELECT 1 FROM latest AS y
    WHERE y.article_id = x.other_id AND y.other_id = x.article_id
      AND y.relation <> 'same')
```

そのため、A が B を same・C を related（同じ案件の別の出来事）と判定し、C が B を same と判定すると、A–B と B–C が
つながって A・B・C が 1 つのグループになる。A–C の related は、どちらの向きの組でもないので使われない。

既存のグループは候補として 1 単位で判定されるので、この食い違いは起きにくく見えるが、次の場合に起きる。

- 1 回の LLM 呼び出し（`llm.story_batch_size` 件）の記事は、呼び出す前の同じグループの状態から候補を選ぶ。同じ
  出来事の記事は日付が近く同じバッチに入りやすいので、A と C がそれぞれ単独の B を same と判定しうる
  （並行する作業者どうしでも同じ）
- 1 件の記事は複数の候補を same にできる。D が B と E を same とすると、B が E を related としていても、組
  D–B と D–E は向きの違う組ではないのでつながる

グループの記事数の上限（`MAX_STORY_SIZE`）は鎖状につながるのを件数で止めるだけで、この食い違いは止めない。

レビューは「グループ内の整合性（日付の幅・類似度・エンティティ）を計算し、低いものを再判定する」ことを提案して
いた。新しい指標を作らなくても、食い違いの証拠は LLM の判定として DB にすでにある。

変更：

- 最新の判定が related か unrelated の組を「つないではいけない組」として `components` に渡す。2 つの集合を
  つなぐとき、両方の記事の間につないではいけない組があれば、そのつなぎは捨てる（件数の上限で捨てるのと同じ扱い）
- 組は今と同じく類似度の高い順につなぐので、強い same が先に残り、食い違いを起こす弱い same が捨てられる
- 捨てた組はログに出す。件数の上限で捨てた組は今と同じく warn、別の出来事の判定で捨てた組は LLM の判定のとおりの
  結果で異常ではないので info にする

やらないこと：

- グループの整合性の点数や再判定の仕組みは作らない。上の変更で、食い違いのあるグループは作られなくなる

## B. `status` にステージごとの失敗の記録を出す

今の `status` はソースごとの記事数と取得状況だけを出す（`src/status.rs`）。各ステージの失敗は `stage_errors` に
記録され、一時的な失敗は 1 時間から倍々の間隔で 5 回まで再試行し、そこで諦める（`MAX_ATTEMPTS`）。諦めた記事は
要約や採点が無いまま残るが、それを知る手段は crawl のログしかない。`LlmFailed` の警告は直近の呼び出しの失敗しか
見ないので、一部の記事だけが諦められている状態は出ない。`help` は `status` を「ステージごとの未処理件数などを
表示」と説明しているが、そうなったことは無い。

変更：

- `status` に、ステージ（とバックエンド・モデル）ごとに「失敗中（上限の回数に達していない）」「諦めた」の件数を
  出す。embedding の失敗は要約ごとの名前で記録されるので、空間ごとにまとめる
- 記事の期間では絞らない。見出しの和訳と embedding は期間を区切らずに処理するので、`pipeline.backlog_days` で
  絞るとその失敗を隠す。ステージごとに範囲を変えると、どのステージがどの範囲を対象にするかの規則を `status` に
  書き写すことになる。範囲の外の「失敗中」の記事は再試行されないので、「再試行する」とは書かない
- 諦めた記事があるステージには、最後に諦めた理由を 1 つ添える（原因を調べる手がかりにする）
- `help` と README の `status` の説明を、実際に出すものに合わせる

やらないこと：

- 「処理を待つ」件数は出さない。数えるには、ステージごとにどのキー（バックエンド・モデル・利用者・プロファイル・
  プロンプトの版・embedding の空間）で対象を選ぶかを crawl と同じに組み立てる必要があり、その規則を `status` に
  書き写すことになる（計画 011 で減らした形）。止まった記事を知るという目的には、失敗の記録で足りる
- Web の警告バナーには出さない。諦めた記事は放っておいても一覧の邪魔にならず、運用の確認は `status` で足りる

## C. 途中で止めて再開しても、止めずに走らせた結果と同じになることを確かめる

今は各ステージに「止める指示で止まる」「呼び出しの最中に止めても失敗を記録しない」テストがある
（`digest::cancel_during_a_call_stops_without_recording_failures` など）。しかし再開できることは、ステージを
またいで組み合わせたときの性質で、1 つのステージのテストでは確かめられない。あるステージが止めたときに
何かを書き残すと、後のステージや次の実行がそれを見て違う結果になりうる。

変更（テストのみ）：

- `pipeline/run.rs` のテストに、要約から後のステージを通しで走らせるテストを足す。LLM は依頼の内容から決まった
  応答を返す偽物（`FakeLlm` の responder）を使う
- 止めずに最後まで走らせた結果と、k 回目の LLM の呼び出しで止める指示を出してから次の実行で再開した結果を、
  k を全通り変えて比べる。比べるのは、成果物（種類・記事・中身）、採点、同じ報道のグループ、`stage_errors`。
  ID と時刻は比べない
- テストが落ちたら、その原因を TDD で直す

## 採らなかった提案と理由

- **評価ラベルの偏りを、評価した場所（一覧・確認枠・検索）ごとに分けて出す**：閾値未満の偏りの無い見積もりは
  確認枠ですでに出している（`render_explore`）。評価は数十件で、さらに場所で分けると件数が足りず、どの指標も
  参考値になる
- **成果物の依存関係（どの入力から作ったか）を明示する**：採点と embedding は要約の成果物の ID をキーにし、
  要約と和訳は元にした本文を `artifact_inputs` に持っている。依存はすでに記録されている。同じ報道の判定は要約が
  作り直されても判定し直さないが、要約の作り直しで出来事が同じかどうかは変わらないので問題にならない
- **embedding と LLM の点数の二重体系の整理**：計画 010 で、評価が溜まってから `eval` で比べて段階 3 を決める
  ことになっている
- **Web の DB の単一ロック（`Arc<Mutex<Db>>`）**：レビュー自身が「今は変えなくてよい」としている。利用者が数人で、
  ロックが律速になっている事実も無い
- **触らないほうがよいもの（DAG 化、PostgreSQL、SPA 化、バックエンドの追加、推薦の複雑化）**：今の方針と同じ
