# ランキングの採点を embedding に一本化し、LLM の採点をやめる

この計画は、何をなぜ決めたかを残す。競合や端のケースの扱いは、各 PR でテストとともに決める。

## 背景

計画 010 の趣旨は、ランキング（一覧・和訳の先回り・補正の学習など）の採点を LLM から embedding に置き換えることだった。
LLM の採点は所有者のサブスクリプションの枠を使うので、利用者の数だけ回すと枠を使い切る。embedding はローカル（r995）や
安い API（社内）で、内積の計算だけで全記事を採点できる。

ところが計画 010 は、段階 3 に「所有者は採点器を選べる（既定 `llm`）」という移行期の保険を置き、段階 3 に進む条件を
「embedding の一致率が LLM と同じ程度なら」とした。その結果、段階 2 の後も一覧は LLM の点数だけを読み、embedding の点数は
保存しても使われないままだった。2026-10-04 に次のことが起きて、この保険が実害になった。

- プロファイルを差し替えると（計画 016）、LLM の点数はプロファイルの hash ごとなので、一覧のほぼ全部が未採点になった。
  次の crawl でも LLM の枠の上限（時間帯ごとの 5 時間枠）で途中までしか採点できなかった。embedding なら次の crawl で数秒で
  全記事を採点し直せる
- 計画 016 の見直しは、案と今のプロファイルを比べるために LLM で採点し直す。評価が増えるほど呼び出しが増える

embedding が順位の質で LLM を上回ることは期待しない。LLM は記事を読んで判断し、embedding は文の近さを測るだけである。
質は「LLM と同じ程度か」ではなく星の評価との一致率で測り、次の手段で上げる。

- 評価からプロファイルを直す（計画 016）
- 評価から学ぶ補正（計画 004）
- 式とモデルの比較（`eval`。式の候補、sarashina など）

## 決めたこと

### ランキングは embedding の点数だけを読む

- 点数を選ぶ SQL の断片（`list_score`）を embedding の点数だけを選ぶものにし、点数を読むすべての箇所をこの断片に通す。
  一覧・検索・詳細・確認枠・フィードと MCP、和訳の先回り（`pending_translate`）、補正の学習（`recommend_examples`）、
  `redo --min-score`、プロファイルの版の一致率と見直しの比較（計画 016）が対象になる
- 採点器の選択（計画 010 の段階 3 の `llm`・`embedding`）は作らない。所有者も embedding だけ
- `[embedding]` の設定が無ければ点数は付かない（一覧は新しい順、最低点なし）

### 最低点は、点数の付いた記事があるときだけ掛ける

一覧の期間に、利用者の今のプロファイルで点数の付いた記事が 1 件以上あるときだけ最低点を掛ける（計画 010 の段階 3 のとおり）。
今の「プロファイルがあれば掛ける」では、`embed rebuild` の直後や、プロファイルを変えてから次の crawl までの間に一覧が空になる。
MCP の検索とフィードも同じ判定を通す。

### 点数の名前と表示

- `ListItem` の `llm_score` は、出どころが embedding になるので中立の名前（`base_score`）にする
- 画面の「LLM {点数}」は「近さ {点数}」にする。embedding の点数には理由の文が無いので、詳細は当たった関心分野と推薦しない話題を出す
- JSON（`/api/articles`）と MCP の `llm_score` は公開のフィールドなので、同じ値で残す。中立の名前のフィールドを足し、`llm_score` は
  使う側が移ったら消す

### 見直しの比較も embedding で行う（計画 016 の変更）

計画 016 の見直しは、今のプロファイルと案を同じ評価で採点して比べる。この採点を LLM ではなく embedding で行う。

- 両方とも保存したベクトルからその場で計算する（`eval --profile` の embedding の候補と同じ）。百分位の基準も同じ時点にそろうので、
  保存した点数（採点した時点の基準で固まっている）と、その場で計算した点数を混ぜて比べることが無い
- 見直しに要る LLM の呼び出しは、案を作る 1 回だけになる。ベクトルは、案で新しくなった好みの文の分だけ作る
- `[embedding]` の設定が無ければ見直しはしない（ランキングが無いので比べる意味が無い）

### LLM の採点をやめる

- crawl の `score` ステージと、要約が採点のために残す呼び出し（`score_reserved_calls`）を外す
- LLM で採点するコード（`pipeline::score`・`prompt::score`・採点待ちの選択）と、`eval --profile` の LLM での採点を消す。
  `eval --profile` は embedding の候補だけを並べる
- 保存済みの LLM の点数は消さない。`eval` は保存した点数をキーごとに並べるので、これまでの LLM の採点と embedding を比べる材料として残る
- 更新案づくりの LLM の設定（今は採点と共用の `score_backend`・`score_model`）は、案づくりの設定として名前を変える

### 履歴の一致率の移行

プロファイルの版の一致率（計画 016）は、退いた版では退いた時点の値で固まる。r995 の最初の版（b4566a7c）は、計画 016 の反映の後に
手で入れたので値を固めておらず、その場で集計している。embedding の点数は古いプロファイルの hash の分を消すので、
一本化した後はこの版の値が出なくなる。反映の前に、今の規則（LLM の点数）での値を固めておく。

## 変更

PR を分けて順に入れる。テストはそれぞれの PR で決める。

1. ランキングを embedding の点数に切り替える
   - 点数を読む箇所を 1 つの断片に通し、embedding の点数を選ぶ
   - 最低点は、点数の付いた記事があるときだけ掛ける
   - 名前と表示（`base_score`、「近さ」、JSON と MCP の互換のフィールド）
2. 見直しの比較を embedding にする（計画 016 の比較から LLM の採点を外す）
3. LLM の採点をやめる（`score` ステージ・採点のコード・`eval --profile` の LLM・設定の名前）
