# オフライン評価 `nucrawler eval`（計画 3 の詳細）

全体計画 [https-chatgpt-com-c-6ab90926-7618-83ee-b-enumerated-lagoon.md](https-chatgpt-com-c-6ab90926-7618-83ee-b-enumerated-lagoon.md) の 3 を実装に落とす。

## Context

推薦の点数は LLM が付けているが、その点数が利用者の反応とどれだけ合っているかを測る手段が無い。
プロファイルやプロンプトを変えても、良くなったのか悪くなったのかは感覚でしか判断できない。
一方、`events` には明示的な反応（👍 up・👎 down・ブックマーク bookmark・見送り dismiss）が既に溜まっていて、そのまま正解ラベルとして使える。
これを使い、採点のキー（プロファイル・バックエンド・モデル・プロンプトの版）ごとに、点数が正例と負例をどれだけ分けられているかを出す。

2026-09-27 時点の本番 DB では、ラベルは 11 件（up 3・bookmark 4・dismiss 4、down 0）で、指標はまだ誤差が大きい。
それでも仕組みを先に入れておけば、反応が溜まるにつれて判断に使えるようになる。

## ラベルの決め方

- 記事ごとに、残っている明示的な反応（up・down・bookmark・dismiss）のうち**最後のもの**で決める。
  - up・bookmark は正例、down・dismiss は負例。
  - 取り消し（undo）は `events` の行を消すので、残っている行が有効な反応。
  - ブックマークは外した後も正例とする。読み終えて外すのが自然な使い方で、外したことは興味が無くなったことを意味しない。全体計画にあった「今も付いているもの」から、この理由で変える。
- open_detail・open_translation は使わない。点数が高い記事ほど開かれやすいので、点数の結果であって正解にならない。

## 3a `feat/eval-command`：既存の採点を評価する（LLM を呼ばない）

### 集計（`src/db/eval.rs`）

- `Db::eval_labels(user_id) -> Vec<Label { article_id, positive: bool, at: String }>`。`at` は、ラベルを決めた反応の時刻。
- `Db::eval_scores(user_id) -> Vec<ScoredLabel>`：ラベルの付いた記事について、キー `(profile_hash, backend, model, prompt_version)` ごとの点数を返す。
  - 点数は、その記事の digest のうち、そのキーで採点された最新の digest のもの。一覧と同じく、最新の digest を優先する。
  - `scored_at`（採点の時刻）も返す。
- 集計は純粋関数 `src/eval.rs` に置く。
  - `auc(pos: &[u8], neg: &[u8]) -> Option<f64>`：正例と負例の組のうち、正例の点数が高い割合。同点は 0.5 とする。どちらかが空なら `None`。
  - 点数帯（10 点刻み。90 帯は 90〜100）ごとの正例と負例の件数。
  - カバー率：ラベルのうち、そのキーで採点済みの件数。
  - **漏れの件数**：採点の時刻がラベルの反応より後の件数。
    - score の版 1 のプロンプトには、直近の反応の見出しが入る。反応の後に採点し直すと、記事自身の見出しがシグナルに入っていた可能性がある。
    - AUC は高めに出うるので、その件数を注記する。

### 表示（`src/eval.rs` の `render`）

- 先頭にラベルの内訳を出す（正例 N・負例 M、種類ごとの件数）。
- 次にキーごとの結果を並べる。既定は、現行のプロファイルの hash と現行の score の `PROMPT_VERSION` のキーだけ。`--all` なら全部。
- 1 キーごとに次を出す。
  - キーと、それが現行かどうか
  - カバー率
  - AUC
  - 漏れの件数
  - 点数帯ごとの表
- 正例か負例が 5 件未満なら「ラベルが少ないため参考値」と注記する。

### CLI

- `Command::Eval`。使い方は `nucrawler eval [--all]`。
- `src/main.rs` の `eval()` は `status()` と同じ形にする。

### テスト（RED を先に）

- `eval_labels`：最後の反応で決まること（dismiss の後に bookmark なら正例）、取り消した反応は使わないこと、open_* は使わないこと。
- `eval_scores`：最新の digest の点数を使うこと、キーごとに分かれること、`scored_at` を返すこと。
- `auc`：完全に分離、逆順、同点、空。
- 点数帯の境界（49 は 40 帯、90 と 100 は 90 帯）。
- `render` の出力（少数の注記、漏れの注記）。
- CLI の解釈。

## 3b `eval --profile FILE`：候補のプロファイルで採点して比べる（LLM を呼ぶ）

3a の後に、別の詳細計画で扱う。先に決めておくべき課題が 1 つある。

- 版 1 の score のプロンプトは直近 20 件の反応の見出しを含む。そのため、候補のプロファイルでラベル付きの記事を採点すると、ラベルそのものがシグナルとして LLM に渡り、評価が甘くなる（漏れ）。
- シグナルを抜いたプロンプトで採点すると、同じ `PROMPT_VERSION` のキーに別のプロンプトの点数が混ざる。
- 解決には、全体計画 4 の「score のプロンプトから直近の反応を外し、版を 2 に上げる」を 3b より先に行う必要がある。
- ただしそうすると、`profile suggest`（4）ができるまでの間、反応が採点に効かない期間ができる。現在の反応は 11 件と少なく影響は小さいが、進め方を変えることになるので、3a の後に利用者に確認する。
